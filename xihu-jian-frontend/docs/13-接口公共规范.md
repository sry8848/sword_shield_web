# 西湖论剑·大会门户 MVP API 公共规范

> 状态：Draft 0.1.0。本文定义首版接口的建议统一约定，待需求评审后冻结。OpenAPI 文件是接口结构的机器可读契约；本文解释跨接口规则。

## 1. 基础约定

| 项目 | 当前草案 |
|---|---|
| OpenAPI 版本 | 3.1.0 |
| API 版本前缀 | `/api/v1` |
| 数据格式 | JSON |
| 字符编码 | UTF-8 |
| 字段命名 | lowerCamelCase |
| 资源 ID | 字符串，避免 JavaScript 大整数精度丢失 |
| 时间格式 | ISO 8601，带时区偏移 |
| 业务时区 | 暂按 `Asia/Shanghai` |
| 默认分页 | `page=1`、`pageSize=10` |
| 最大分页 | `pageSize=100` |

示例完整 URL：`GET /api/v1/public/events?page=1&pageSize=10`。

## 2. URL 与 HTTP 方法

- URL 使用名词表达资源，集合使用复数形式，例如 `/events`、`/registrations`。
- 查询资源使用 GET。
- 创建资源使用 POST。
- 局部修改使用 PATCH。
- 整体替换某个关系集合使用 PUT，例如替换用户角色集合。
- 发布、下线、核验等明确业务动作使用 POST 子资源路径。
- URL 不使用动词堆叠，例如避免 `/getEventList`、`/doPublish`。
- 路径参数使用 `{eventId}` 形式；查询条件放在 Query。

## 3. 统一成功响应

成功请求统一返回：

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {},
  "traceId": "trace-example-001",
  "timestamp": "2026-11-06T14:00:00+08:00"
}
```

- `code`：机器可判断的业务码，成功固定为 `SUCCESS`。
- `message`：面向开发调试的简短说明，不建议前端依赖它做业务分支。
- `data`：实际业务数据。
- `traceId`：请求追踪标识，排查问题时提供给后端。
- `timestamp`：服务端生成响应的时间。

列表接口的 `data` 统一采用：

```json
{
  "items": [],
  "pageInfo": {
    "page": 1,
    "pageSize": 10,
    "total": 0,
    "totalPages": 0
  }
}
```

## 4. HTTP 状态码与错误响应

| HTTP 状态 | 含义 | 示例业务码 |
|---|---|---|
| 400 | 请求格式或参数错误 | `INVALID_ARGUMENT` |
| 401 | 未登录或令牌无效/过期 | `UNAUTHENTICATED` |
| 403 | 已登录但无操作权限 | `FORBIDDEN` |
| 404 | 资源不存在 | `RESOURCE_NOT_FOUND` |
| 409 | 当前业务状态冲突 | `ALREADY_REGISTERED`、`ALREADY_CHECKED_IN`、`EVENT_FULL` |
| 422 | 参数格式正确但违反业务规则 | `REGISTRATION_CLOSED`、`EVENT_NOT_STARTED` |
| 500 | 未预期的服务端错误 | `INTERNAL_ERROR` |

错误响应建议统一为：

```json
{
  "code": "ALREADY_REGISTERED",
  "message": "你已报名该场次",
  "details": {},
  "traceId": "trace-example-002",
  "timestamp": "2026-11-06T14:00:00+08:00"
}
```

约定：
- 前端优先根据 HTTP 状态和 `code` 做分支，不根据中文 message 判断。
- `details` 只放必要的结构化上下文，不返回堆栈、SQL、令牌或敏感信息。
- 参数校验错误可以在 `details` 中返回字段级错误，例如 `{ "field": "phone", "reason": "INVALID_FORMAT" }`。
- 未登录与无权限必须区分：401 表示身份未建立，403 表示身份已建立但权限不足。

## 5. 身份认证

当前草案：
- 登录成功返回 `accessToken`、`refreshToken`、`tokenType`、`expiresIn`。
- 受保护接口在请求头携带 `Authorization: Bearer <accessToken>`。
- 访问令牌过期后调用 `POST /auth/refresh`。
- 退出登录调用 `POST /auth/logout`，服务端使刷新令牌失效。
- 普通参会账号和后台工作人员暂按同一账号体系处理；后台接口额外校验角色/权限。

安全注意：
- 不应把密码、完整手机号、刷新令牌或二维码签名载荷写入普通日志。
- refreshToken 的传输和存储方式（HttpOnly Cookie 或请求体）尚未冻结。
- 前端不应仅依靠隐藏按钮实现权限控制；服务端必须逐接口校验权限。
- 登录、注册、刷新接口应有频率限制；具体阈值由安全方案确定。

## 6. 分页、筛选与排序

- 页码从 1 开始。
- 默认 `page=1`、`pageSize=10`，最大 `pageSize=100`。
- 返回 `items` 和 `pageInfo`，`total` 表示满足筛选条件的总记录数。
- 无数据时返回 `items: []`、`total: 0`、`totalPages: 0`。
- 日期筛选使用 `YYYY-MM-DD`；时间范围使用带时区的 ISO 8601。
- MVP 默认排序由接口说明给出；如需用户排序，再增加明确的 `sortBy`、`sortOrder`，不接受任意 SQL 字段。

## 7. 时间、空值与枚举

- 日期时间统一使用 ISO 8601，例如 `2027-05-20T09:00:00+08:00`。
- 数据库存储建议统一 UTC，接口转换为明确时区；业务展示按大会时区。
- `null` 表示字段存在但当前没有值；字段缺失通常表示本次 PATCH 不修改该字段。
- 空字符串不应被当作 `null` 的替代品；文本字段是否允许空字符串需按字段定义。
- 枚举值使用大写英文常量，前端维护“枚举值→中文文案”的映射，不把中文文案作为接口值。

### 7.1 场次状态（草案）

- `DRAFT`：草稿。
- `PUBLISHED`：已发布。
- `UNPUBLISHED`：已下线。
- `FINISHED`：已结束。

发布前必须满足必要字段校验。已结束状态是否自动计算、下线后是否允许再次发布，待确认。

### 7.2 报名状态（草案）

- `REGISTERED`：报名成功，尚未核验。
- `CHECKED_IN`：已完成现场核验。
- `CANCELLED`：已取消/失效的历史状态；本版暂不提供用户自主取消接口，是否需要后台取消能力待确认。

### 7.3 报名开放状态（草案）

- `NOT_OPEN`：未到开放时间。
- `OPEN`：开放报名。
- `CLOSED`：已截止或未开放报名。
- `FULL`：达到名额上限。

## 8. 报名业务约束（待确认）

当前接口草案采用以下建议：
- 只有登录用户可以提交报名。
- 同一用户对同一场次默认只能成功报名一次。
- 活动未发布、未到报名开始时间、已过报名截止时间时不可报名。
- 若配置 `capacity`，达到名额上限后停止新报名；`capacity=null` 表示不限额。
- 是否允许取消报名、取消后是否释放名额、报名表字段是否需要组织/职位，需需求确认。
- 即使不建设高并发抢票架构，后端仍需保证同一用户重复请求和名额竞争不会产生重复记录或超额数据。

## 9. 凭证与现场核验约束（待确认）

当前接口草案采用“一次提交即核验并登记到场”的方式：
- 凭证二维码由后端生成不可伪造的载荷，前端只负责展示二维码。
- 手动输入凭证编号和扫描二维码走同一个核验接口。
- 核验必须校验场次归属、报名状态、凭证有效性。
- 一张凭证只能成功核验一次；重复核验返回 409 / `ALREADY_CHECKED_IN`。
- 核验成功后记录核验时间、操作人员和输入方式。
- 是否需要“先校验预览、工作人员确认后再写入”，是否允许撤销误核验，待确认。

## 10. RBAC 基础权限约定

当前建议的内置角色：
- `SUPER_ADMIN`：系统管理员。
- `EVENT_OPERATOR`：会务运营，可管理场次和报名。
- `CHECKIN_STAFF`：现场核验员，可执行授权核验并查看必要信息。
- `DATA_OPERATOR`：数据运营，可查看统计。

权限码采用 `resource:action`，例如：
- `event:read`
- `event:create`
- `event:update`
- `event:publish`
- `registration:read`
- `checkin:create`
- `checkin:read`
- `statistics:read`
- `user:read`
- `user:assign_role`

MVP 草案暂采用内置角色 + 角色分配，不提供自定义角色 CRUD 和复杂数据范围授权。角色权限映射必须由后端维护；前端通过 `/admin/me` 获取当前用户权限后控制菜单和按钮显示。

## 11. 数据安全与隐私

- 用户只能查询自己的报名和凭证。
- 运营人员只能在其权限范围内查看报名数据；手机号等个人信息按最小必要原则展示或脱敏。
- 核验员只获取完成核验所必需的参会人信息。
- 管理接口必须服务端鉴权，不能依赖前端传入的 `userId` 决定数据归属。
- 二维码载荷不得直接包含手机号、邮箱等明文个人信息。
- 日志不记录密码、完整令牌、完整二维码载荷。

## 12. 变更管理

- OpenAPI 文件是接口结构的唯一契约源，提交 Git 时与代码变更一起评审。
- 破坏性变更（删除字段、改字段类型、改变枚举语义、改变认证要求）必须显式评审。
- 新增可选字段通常可兼容；前端仍应对未知枚举和可选字段做容错。
- 每次契约变更更新 `info.version` 或在 Git 提交中记录变更原因。
- Apifox 用于导入、查看、Mock 和调试；不要在 Apifox 与 Git 中长期维护两份互不一致的接口定义。
