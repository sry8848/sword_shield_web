# MVP 1.0 接口待确认事项

> 下方 P0–P2 是接口与业务评审清单，OpenAPI 0.1.0 暂按表中草案编写。优先处理 P0，再冻结接口契约。已确定的前端架构见 [01 技术选型与架构设计](01-技术选型与架构设计.md)，实施差距见文末。

## P0：会改变接口结构或核心业务流程

| 编号 | 主题 | 当前草案 | 需要确认的问题 | 建议 |
|---|---|---|---|---|
| D01 | 用户账号形式 | 登录使用 `account + password`，注册额外要求 `displayName` | 登录请求如何表达手机号约束？后续注册的手机号验证流程和验证码规则如何设计？ | 已确认以手机号作为唯一登录标识，使用密码登录。本期不实现注册，注册验证留待注册模块设计。 |
| D02 | 普通用户与后台账号 | 目前仅定义统一的 `POST /auth/login` | 前后台登录接口分别采用什么路径？ | 已确认共用账号体系，前后台设独立登录入口，后台登录要求至少一个有效后台角色。具体 API 路径待契约设计。 |
| D03 | 令牌方案 | Refresh Token 通过 HttpOnly Cookie 传输，业务接口使用 Bearer Access Token | 两类令牌的具体有效期多长？刷新时是否轮换 Refresh Token？前端部署在哪些来源？ | 已确认允许多设备登录，前后台会话独立，退出仅使当前应用的当前会话失效。使用短期 Access Token，部署时按 [06 的认证约定](06-接口与数据规范.md#81-认证约定) 配置 Cookie、CORS 和 CSRF 防护。 |
| D04 | 报名表字段 | 姓名、手机号必填；组织、职位、备注选填 | 实际报名需要收集哪些字段？是否从个人资料自动带入？ | 先只收集业务必需字段，避免收集无用个人信息 |
| D05 | 重复报名规则 | 同一用户同一场次只能报名一次 | 是否允许同一手机号替他人报名？是否支持多人同行报名？ | MVP 建议一账号一人一条报名记录 |
| D06 | 名额限制 | `capacity=null` 表示不限额；有上限则满额拒绝 | 普通场次是否需要容量上限？满额是否显示“已满”？是否允许后台超额？ | 普通报名可先支持可选容量，但不建设抢票/候补 |
| D07 | 报名取消 | 当前不提供用户自主取消接口；保留历史 `CANCELLED` 状态 | MVP 是否要求用户取消报名？是否允许运营人员取消？取消后是否释放名额？ | 如果验收要求有取消，再补 `POST /me/registrations/{id}/cancel`，不要先默认实现 |
| D08 | 场次与活动模型 | `Event` 表示一个可报名的议程场次；Conference 单独提供大会基础信息 | 现有需求中的“活动”是否全部按“场次”管理？一个活动是否包含多个子场次？ | MVP 先用一个 Event 对应一个可报名场次，复杂父子活动关系后置 |
| D09 | 嘉宾和会场数据 | 前台有读取接口；本版没有嘉宾/会场后台维护接口 | 嘉宾和会场数据由谁维护？是否已经有初始化数据或由其他模块提供？ | 首期可先由配置/种子数据维护，若运营必须在线维护再补后台接口 |
| D10 | 现场核验交互 | `POST /admin/check-ins` 一次完成校验和核验写入 | 扫码后立即核销，还是先展示姓名/场次供工作人员确认再核销？ | 推荐先展示关键信息再确认；若采用此方案，应拆成预校验和确认两个接口 |
| D11 | 凭证内容 | 后端生成签名载荷；前端生成二维码；支持手动输入凭证编号 | 二维码是静态码还是动态码？是否需要防截图转发？是否支持离线核验？ | MVP 建议在线核验的签名静态码；动态码、防转发和离线核验后置 |
| D12 | 核验权限范围 | `CHECKIN_STAFF` 可以核验；暂未定义按场次授权 | 核验员能核验所有场次，还是只能核验分配给自己的场次？ | MVP 若只有少量场次可先按角色授权；若有多会场并行执行，需增加场次数据范围 |

## P1：影响后台管理和统计口径

| 编号 | 主题 | 当前草案 | 需要确认的问题 | 建议 |
|---|---|---|---|---|
| D13 | 内置角色 | `SUPER_ADMIN`、`EVENT_OPERATOR`、`CHECKIN_STAFF`、`DATA_OPERATOR` | 是否需要客服、内容运营等角色？首期是否只需这四类？ | 只保留首期实际使用的角色 |
| D14 | 角色权限 | 预设角色与权限码；只允许给账号分配角色 | 管理员是否需要自定义角色、编辑权限集合？ | MVP 使用固定角色矩阵，避免先做通用权限配置平台 |
| D15 | 后台账号创建 | 当前接口只查询账号和分配角色 | 后台账号如何产生？公开注册后由管理员授权，还是管理员创建账号？ | 推荐先由管理员给已注册账号分配后台角色 |
| D16 | 数据权限 | 暂不做细粒度数据范围，角色权限为主 | 是否存在分会场/分活动隔离？核验员能否看到其他活动报名人？ | 如果确实有不同承办方或场次隔离，必须在 MVP 加数据范围 |
| D17 | 统计口径 | 报名数=有效报名记录数；到场数=成功核验数；到场率=到场数/报名数 | 已取消报名是否排除？统计按报名时间还是活动时间？跨日期活动如何归属？ | 指标旁展示统计时间范围与口径 |
| D18 | 报表导出 | 当前只定义查询，不含导出 | MVP 是否需要 Excel/CSV 导出？导出哪些字段？ | 若甲方验收要求导出，再增加异步/同步导出接口 |
| D19 | 首页内容 | 首页接口返回大会信息和精选场次，不返回独立公告 | 首页是否必须有重要通知？通知是否需要后台管理？ | 若通知是首期硬需求，增加公告列表/公告管理；否则先用静态配置 |
| D20 | 场次编辑 | 创建后默认草稿；发布/下线独立动作 | 已发布场次能否直接编辑？编辑时间/地点后是否通知已报名用户？ | MVP 先允许编辑，但对关键字段变更提示影响；通知功能后置 |
| D21 | 文件上传 | 封面字段先接收 URL，没有上传 API | 封面由对象存储、现有文件服务还是本地上传提供？ | 先确认项目现有文件服务；若没有，再单独设计上传接口 |
| D22 | 跨时区活动 | 本届杭州大会按 `Asia/Shanghai` 展示 | 是否存在需要单独指定展示时区的线上活动或其他地区活动？ | 遵循 [06 的时间约定](06-接口与数据规范.md#91-时间)，有跨时区活动需求时再确定配置位置 |

## P2：可在第一轮评审后决定

- 是否需要用户修改个人资料接口；当前只定义注册、登录和当前用户信息。
- 是否需要用户主动取消报名。
- 是否需要报名凭证重新生成/作废。
- 是否需要撤销误核验及核验异常处理。
- 是否需要活动删除；当前采用下线保留历史记录。
- 是否需要统计数据导出。
- 是否需要短信通知、邮件通知、报名成功通知。
- 是否需要报名渠道来源字段；当前不做渠道归因统计。

## 建议评审顺序

先确认以下 8 项，它们最可能导致 OpenAPI 结构调整：

1. D01 手机号登录请求约束。
2. D03 令牌有效期、轮换和部署来源。
3. D04 报名表单字段。
4. D07 是否允许取消报名。
5. D08 Event 与场次的关系。
6. D10 扫码后是否立即核验。
7. D12 核验员的数据范围。
8. D17 报名数与到场率口径。

确认后再冻结 OpenAPI 1.0.0；在此之前请将当前版本视为评审草案。

## 前端骨架后续整改

以下是已定架构的实施差距。业务与接口评审事项见上方 P0–P2。

| 范围 | 当前骨架 | 后续整改 |
|---|---|---|
| 工程组织 | pnpm Workspace、Portal、Admin 和 Shared 已存在，两端各有独立的启动与构建入口和基础样式。 | 首个实际业务按所属应用的 Feature 接入，出现跨 Feature 调用时定义公共接口。 |
| API 与 HTTP | 共享 Axios 已有默认超时、令牌注入、并发刷新和错误解包，认证通过回调注入。两端入口暂无业务 API。 | 需要接口时在所属 Feature 实现 API，将查询取消信号传入 Axios，并保留取消语义。 |
| 契约与模型 | 仓库有 OpenAPI 草案。HTTP 层使用内部响应包装类型完成解包和错误转换。 | 接入 `openapi-typescript`，从契约生成 DTO，按需转换展示和表单模型。 |
| 查询与路由 | 两端目前仅有用于验证挂载的应用根组件。 | 随实际业务建立路由，接入 TanStack Query，按路由和有效查询条件建立稳定 Key，实现读写及失效逻辑。 |
| 会话与权限 | HTTP 层提供令牌读取、刷新及失效回调。 | 按实际登录和权限需求接入会话 Store、路由守卫和私有查询清理，联调 Cookie、权限和 Gateway。 |
| 工程质量 | 已有 ESLint、TypeScript、Vitest、Playwright 配置与脚本，保留共享 HTTP 单元测试和两端启动冒烟测试。前端锁文件和 GitHub Actions 工作流尚未入库。 | 入库 pnpm 锁文件并启用冻结安装，配置合并门禁与契约、依赖边界检查，随业务补充认证、查询和关键规则测试。 |
| 部署 | 两端有独立构建与环境变量配置。仓库未提供生产部署流水线。 | 配置独立部署并验证 History fallback、真实 API、Cookie 和 Gateway。 |
