## 1. 文档定位与契约管理

### 1.1 文档职责

本文统一原《接口公共规范》和《接口与数据规范》的内容，分为两类规则：

1.  **API 协议规则**：约束接口路径、HTTP
    方法、请求参数、响应结构、错误码、认证、分页、时间、枚举和业务约束。
2.  **工程接入规则**：约束前端如何调用 API、如何处理认证和错误、如何组织
    API 客户端，以及如何使用 Mock。

本文不代替具体接口定义。每个业务接口的路径、方法、参数、请求体、响应体、错误响应和认证要求，必须在
OpenAPI 文件中明确描述。

### 1.2 唯一契约来源

仓库中的 `openapi/openapi.yaml` 是项目对外 API
结构的唯一机器可读契约来源。

-   本文定义跨接口通用规则。
-   OpenAPI 定义具体接口及其 Schema。
-   Apifox 用于导入 OpenAPI、评审、Mock 和调试，不与 Git 中的 OpenAPI
    长期维护两份互不一致的接口定义。
-   前端和后端均应以经过评审的 OpenAPI 契约为实现依据。

### 1.3 接入现有后端时的处理

接入现有 Spring Boot / Gateway
或其他既有服务前，必须核对实际实现，包括：

-   URL 与 HTTP 方法；
-   请求参数和 DTO；
-   响应包装及分页结构；
-   错误码和 HTTP 状态码；
-   认证与权限要求；
-   时间、金额、文件等数据格式。

如果实际实现与已评审的 OpenAPI 不一致，应先评估并明确选择：

1.  修改后端，使其符合现有契约；或
2.  经评审修改 OpenAPI，并同步调整前后端实现。

不得让页面或业务模块各自兼容不同的接口格式，也不得以"当前后端就是这样"为由绕过契约评审。

## 2. 基础约定

  项目           统一约定
  -------------- ----------------------------------------
  OpenAPI 版本   3.1.0
  API 版本前缀   `/api/v1`
  数据格式       JSON
  字符编码       UTF-8
  字段命名       `lowerCamelCase`
  资源 ID        字符串，避免 JavaScript 大整数精度丢失
  日期时间       ISO 8601，必须带时区偏移
  业务时区       本届杭州大会使用 `Asia/Shanghai`
  默认分页       `page=1`、`pageSize=10`
  最大分页       `pageSize=100`

示例：

``` http
GET /api/v1/public/events?page=1&pageSize=10
Accept: application/json
```

除文件上传、文件下载等明确的特殊场景外，请求和响应默认使用 JSON。

## 3. URL 与 HTTP 方法

### 3.1 URL 规则

-   URL 使用名词表达资源，集合名称使用复数形式，例如
    `/events`、`/registrations`。
-   所有对外业务 API 统一使用 `/api/v1` 前缀。
-   路径参数用于标识具体资源，例如 `/events/{eventId}`。
-   查询条件、分页和排序参数放在 Query 中。
-   不使用动词堆叠式路径，例如 `/getEventList`、`/doPublish`。
-   不在 URL 中放置密码、Token、手机号等敏感信息。
-   公共接口、用户接口和管理接口可以通过清晰的资源路径区分，例如
    `/public/events`、`/registrations`、`/admin/users`。

### 3.2 HTTP 方法语义

  方法     统一语义                       示例
  -------- ------------------------------ -------------------------------
  GET      查询资源，不产生业务副作用     `GET /api/v1/events/123`
  POST     创建资源或执行明确的业务动作   `POST /api/v1/events`
  PUT      整体替换资源或关系集合         `PUT /api/v1/users/123/roles`
  PATCH    局部修改资源                   `PATCH /api/v1/events/123`
  DELETE   删除资源                       `DELETE /api/v1/events/123`

发布、下线、核验等明确业务动作，使用 POST 子资源路径，例如：

``` http
POST /api/v1/admin/events/123/publish
POST /api/v1/admin/events/123/unpublish
POST /api/v1/admin/check-ins
```

是否允许删除、采用软删除还是物理删除，由具体业务接口定义；不得仅根据
HTTP 方法推断数据删除策略。

## 4. 请求参数规范

### 4.1 通用规则

-   请求字段采用 `lowerCamelCase`。
-   ID 使用字符串。
-   分页参数统一使用 `page` 和 `pageSize`。
-   日期筛选使用 `YYYY-MM-DD`。
-   日期时间范围使用带时区偏移的 ISO 8601。
-   请求参数的类型、是否必填、默认值、长度和取值范围，必须在 OpenAPI
    中明确。
-   不允许把敏感信息放入 URL Query 或路径参数。

### 4.2 金额

金额字段必须在 OpenAPI 中明确精度和传输方式，不得让前后端自行猜测。

可采用以下形式：

-   最小货币单位整数，例如人民币分；
-   Decimal 字符串，例如 `"123.45"`。

具体字段应选择一种并保持一致。涉及金额的接口必须明确币种、单位和精度。

### 4.3 文件

文件上传使用
`multipart/form-data`。文件字段名称、数量限制、大小限制和允许类型由具体接口定义。

文件下载应在 OpenAPI
中明确响应媒体类型及文件内容处理方式，不应强行套用普通 JSON 数据结构。

## 5. 统一响应结构

### 5.1 成功响应

普通 JSON 成功响应统一使用以下结构：

``` json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {},
  "traceId": "trace-example-001",
  "timestamp": "2026-11-06T14:00:00+08:00"
}
```

字段说明：

  ----------------------------------------------------------------------------------------------------------
  字段                    类型                    说明
  ----------------------- ----------------------- ----------------------------------------------------------
  `code`                  string                  机器可判断的业务码，成功固定为 `SUCCESS`

  `message`               string                  简短说明，供调试或展示；前端不得依赖中文文案进行业务分支

  `data`                  object / array /        实际业务数据
                          primitive / null        

  `traceId`               string                  请求追踪标识，用于排查问题

  `timestamp`             string                  服务端生成响应的时间，采用带时区偏移的 ISO 8601
  ----------------------------------------------------------------------------------------------------------

`traceId` 和 `timestamp` 在普通 JSON 成功响应中必须返回。

### 5.2 错误响应

错误响应统一使用以下结构：

``` json
{
  "code": "ALREADY_REGISTERED",
  "message": "你已报名该场次",
  "details": {},
  "traceId": "trace-example-002",
  "timestamp": "2026-11-06T14:00:00+08:00"
}
```

字段说明：

  字段          类型     说明
  ------------- -------- --------------------------------------------
  `code`        string   稳定的机器可判断错误码
  `message`     string   简短错误说明，不作为前端业务判断依据
  `details`     object   可选的结构化上下文；没有必要信息时可以省略
  `traceId`     string   请求追踪标识
  `timestamp`   string   服务端生成响应的时间

错误响应中的 `traceId` 和 `timestamp` 必须返回。

`details`
只允许放置必要的结构化上下文，不得返回堆栈、SQL、内部服务地址、令牌或其他敏感信息。

参数校验错误可以返回字段级信息，例如：

``` json
{
  "code": "INVALID_ARGUMENT",
  "message": "请求参数不合法",
  "details": {
    "field": "phone",
    "reason": "INVALID_FORMAT"
  },
  "traceId": "trace-example-003",
  "timestamp": "2026-11-06T14:00:00+08:00"
}
```

### 5.3 TypeScript 类型参考

前端共享请求层可使用以下类型表达统一响应：

``` typescript
export interface ApiEnvelope<T> {
  code: string
  message: string
  data: T
  traceId: string
  timestamp: string
}

export interface ApiError {
  code: string
  message: string
  details?: Record<string, unknown>
  traceId: string
  timestamp: string
}
```

文件下载等非 JSON 响应属于特殊场景，应由具体接口单独定义，不强制包装为
`ApiEnvelope<T>`。

## 6. 分页、筛选与排序

### 6.1 请求分页参数

-   页码从 1 开始。
-   默认 `page=1`。
-   默认 `pageSize=10`。
-   最大 `pageSize=100`。
-   超出允许范围时，接口应按 OpenAPI 中声明的校验规则处理。

### 6.2 统一分页响应

分页列表的 `data` 统一采用 `items + pageInfo`。固定字典等非分页集合只返回 `data.items`，例如 `GET /api/v1/admin/roles` 和 `GET /api/v1/admin/permissions`。

``` json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {
    "items": [],
    "pageInfo": {
      "page": 1,
      "pageSize": 10,
      "total": 0,
      "totalPages": 0
    }
  },
  "traceId": "trace-example-004",
  "timestamp": "2026-11-06T14:00:00+08:00"
}
```

TypeScript 类型参考：

``` typescript
export interface PageInfo {
  page: number
  pageSize: number
  total: number
  totalPages: number
}

export interface PageResult<T> {
  items: T[]
  pageInfo: PageInfo
}
```

字段说明：

-   `items`：当前页数据。
-   `pageInfo.page`：当前页码。
-   `pageInfo.pageSize`：当前页大小。
-   `pageInfo.total`：满足筛选条件的总记录数。
-   `pageInfo.totalPages`：总页数。

无数据时返回 `items: []`、`total: 0`、`totalPages: 0`。

前端表格组件如果使用 `records` 等内部字段，可以在 API 适配层转换；HTTP
接口不得因此改变统一分页结构。

### 6.3 筛选与排序

-   筛选字段由具体接口定义。
-   默认排序规则由接口说明给出。
-   只有确实需要用户选择排序时，才增加 `sortBy`、`sortOrder`。
-   `sortOrder` 应使用明确的枚举值，例如 `ASC`、`DESC`。
-   不接受任意 SQL 字段或未经约束的排序表达式。

## 7. HTTP 状态码与错误码

### 7.1 HTTP 状态码约定

  ---------------------------------------------------------------------------------------------------------------------
  HTTP 状态码             含义                               业务场景示例
  ----------------------- ---------------------------------- ----------------------------------------------------------
  400                     请求格式或参数错误                 `INVALID_ARGUMENT`

  401                     未登录、身份未建立或访问令牌无效   `UNAUTHENTICATED`、`ACCESS_TOKEN_EXPIRED`

  403                     已建立身份，但没有操作权限         `FORBIDDEN`

  404                     资源不存在                         `RESOURCE_NOT_FOUND`

  409                     当前业务状态冲突                   `ALREADY_REGISTERED`、`ALREADY_CHECKED_IN`、`EVENT_FULL`

  422                     参数格式正确，但不满足业务规则     `REGISTRATION_CLOSED`、`EVENT_NOT_STARTED`

  500                     未预期的服务端错误                 `INTERNAL_ERROR`
  ---------------------------------------------------------------------------------------------------------------------

### 7.2 前端错误处理原则

-   前端优先根据 HTTP 状态码和稳定的 `code` 判断处理方式。
-   不根据 `message` 的中文文本进行业务分支。
-   401、403 必须区分：401 表示身份未建立或认证无效；403
    表示身份已建立但权限不足。
-   409 用于表达业务状态冲突。
-   422 用于表达参数格式正确但业务规则校验不通过。
-   5xx 应提示服务暂不可用，并保留 `traceId` 供排查。
-   网络错误应提示网络不可用，并根据请求场景允许用户重试。
-   错误提示不得泄漏堆栈、SQL、内部服务地址或敏感字段。

### 7.3 错误码维护

错误码应稳定、唯一、可供程序判断。新增或修改错误码时，应同步更新 OpenAPI
和相关前端类型或处理逻辑。

已定义具体业务错误码的场景使用对应的 `code`。草案尚未细分的 409、422 场景可分别使用 `BUSINESS_CONFLICT`、`BUSINESS_RULE_VIOLATION`。

错误码建议采用大写英文常量，例如：

``` text
SUCCESS
INVALID_ARGUMENT
UNAUTHENTICATED
ACCESS_TOKEN_EXPIRED
REFRESH_TOKEN_EXPIRED
FORBIDDEN
RESOURCE_NOT_FOUND
ALREADY_REGISTERED
ALREADY_CHECKED_IN
EVENT_FULL
REGISTRATION_CLOSED
EVENT_NOT_STARTED
INTERNAL_ERROR
```

受 Bearer 保护的接口在 Access Token 过期时返回 `401` / `ACCESS_TOKEN_EXPIRED`。刷新或退出接口在服务端识别出 Refresh Token 已过期时返回 `401` / `REFRESH_TOKEN_EXPIRED`。所需令牌缺失或无效时返回 `401` / `UNAUTHENTICATED`。

## 8. 身份认证与 Token 刷新

### 8.1 认证约定

当前草案采用 Access Token + Refresh Token：

-   注册成功建立会话或登录成功时，服务端通过 `Set-Cookie` 下发 `refreshToken`，响应体中的会话数据返回 `accessToken`、`tokenType`、`expiresIn` 和 `user`。
-   受保护接口通过请求头携带 `Authorization: Bearer <accessToken>`。
-   刷新和退出分别调用 `POST /api/v1/auth/refresh` 和 `POST /api/v1/auth/logout`，浏览器自动发送 Cookie。两个接口均无需请求体或 Bearer 访问令牌。若刷新时签发了新的 Refresh Token，服务端通过 `Set-Cookie` 更新 Cookie。
-   退出成功时，服务端使当前 Refresh Token 失效，并以相同名称和路径下发 `Max-Age=0` 的 Cookie。
-   普通参会账号和后台工作人员暂按同一账号体系处理；后台接口额外校验角色和权限。
-   Cookie 设置 `HttpOnly`、`Secure`、`Path=/api/v1/auth`，省略 `Domain`，默认 `SameSite=Lax`。如需跨站部署，部署评审需确定浏览器兼容性和 CSRF 防护，再启用 `SameSite=None`。
-   浏览器跨源调用注册、登录、刷新、退出时启用凭证模式（Axios `withCredentials: true`）。网关或 API 对受信前端返回精确的 `Access-Control-Allow-Origin` 和 `Access-Control-Allow-Credentials: true`。认证接口需校验浏览器请求来源以防止 CSRF。

### 8.2 前端 401 处理

不能把所有 401
都直接处理为清除登录态。应区分访问令牌过期、刷新令牌失效和其他认证失败。

建议流程：

1.  受保护接口返回 `401`，且错误码明确表示 `ACCESS_TOKEN_EXPIRED`
    时，尝试刷新 Access Token。
2.  刷新成功后，更新访问令牌，并对原请求最多重试一次。
3.  刷新接口返回
    `REFRESH_TOKEN_EXPIRED`，或刷新失败且无法恢复登录态时，清理本地登录态并进入登录流程。
4.  原请求重试后仍返回 401，不得继续循环刷新。
5.  登录、注册、刷新等认证接口自身返回 401 时，不得对其无限触发刷新。
6.  403 表示权限不足，不触发 Token 刷新。
7.  多个请求同时遇到 Access Token
    过期时，前端应尽量共用一次刷新请求，避免并发刷新造成状态竞争。

如果后端暂时不能提供明确的过期错误码，应先在认证接口契约中确定可可靠区分的处理方式，再实现前端刷新逻辑；不得仅凭所有
401 一律刷新。

### 8.3 安全要求

-   不应把密码、完整手机号、Refresh Token 或二维码签名载荷写入普通日志。
-   登录、注册、刷新接口应有频率限制，具体阈值由安全方案确定。
-   前端不应仅依靠隐藏按钮实现权限控制，服务端必须逐接口校验权限。

## 9. 时间、空值与枚举

### 9.1 时间

-   接口请求和响应中表示具体时刻的日期时间必须使用 ISO 8601，并带 `Z` 或明确的时区偏移。例如 `2027-05-20T09:00:00+08:00` 与 `2027-05-20T01:00:00Z` 表示同一时刻。禁止传输缺少偏移量的日期时间。
-   数据库存储建议统一使用 UTC。
-   本届杭州大会的业务时间必须通过共享时间工具按 `Asia/Shanghai` 展示。格式化时必须显式指定时区，禁止依赖浏览器或操作系统默认时区。
-   正式业务表单录入大会当地时间时，必须按大会时区解释输入并生成带偏移量的接口值。已有明确偏移量的输入应保留其所表示的时刻。
-   仅表示日期、不表示具体时刻的字段使用 `YYYY-MM-DD`。

### 9.2 空值与 PATCH

-   `null` 表示字段存在，但当前没有值。
-   PATCH 请求中字段缺失通常表示本次不修改该字段。
-   空字符串不能默认视为 `null` 的替代品。
-   文本字段是否允许空字符串，必须由具体字段定义。

### 9.3 枚举

-   枚举值使用大写英文常量。
-   前端维护"枚举值 → 展示文案"的映射。
-   不把中文展示文案作为接口枚举值。
-   前端应对未知枚举值和新增可选字段保持容错，避免因服务端扩展而直接崩溃。

### 9.4 场次状态（草案）

  枚举值          含义
  --------------- --------
  `DRAFT`         草稿
  `PUBLISHED`     已发布
  `UNPUBLISHED`   已下线
  `FINISHED`      已结束

发布前必须满足必要字段校验。已结束状态是否自动计算、下线后是否允许再次发布，待确认。

### 9.5 报名状态（草案）

  枚举值         含义
  -------------- ------------------------
  `REGISTERED`   报名成功，尚未核验
  `CHECKED_IN`   已完成现场核验
  `CANCELLED`    已取消或失效的历史状态

本版暂不提供用户自主取消接口；是否需要后台取消能力待确认。

### 9.6 报名开放状态（草案）

  枚举值       含义
  ------------ --------------------
  `NOT_OPEN`   尚未开始报名，例如场次仍处于草稿或未到报名开始时间
  `OPEN`       正在开放报名
  `CLOSED`     报名已截止
  `FULL`       达到名额上限

## 10. 报名业务约束（待确认）

当前接口草案采用以下建议：

-   只有登录用户可以提交报名。
-   同一用户对同一场次默认只能成功报名一次。
-   活动未发布、未到报名开始时间、已过报名截止时间时不可报名。
-   如果配置 `capacity`，达到名额上限后停止新报名。
-   `capacity = null` 表示不限额。
-   是否允许取消报名、取消后是否释放名额、报名表是否需要组织或职位字段，需需求确认。
-   即使 MVP
    不建设高并发抢票架构，后端仍必须保证重复请求不会产生重复报名记录，也不能因并发竞争产生超额数据。

## 11. 凭证与现场核验约束（待确认）

当前接口草案采用"一次提交即核验并登记到场"的方式：

-   凭证二维码由后端生成不可伪造的载荷，前端只负责展示二维码。
-   手动输入凭证编号和扫描二维码走同一个核验接口。
-   核验必须校验场次归属、报名状态和凭证有效性。
-   一张凭证只能成功核验一次。
-   重复核验返回 `409` / `ALREADY_CHECKED_IN`。
-   核验成功后记录核验时间、操作人员和输入方式。
-   是否需要"先校验预览、工作人员确认后再写入"，以及是否允许撤销误核验，待确认。

二维码载荷不得直接包含手机号、邮箱等明文个人信息。

## 12. RBAC 基础权限约定

### 12.1 内置角色（草案）

  角色               职责
  ------------------ ------------------------------------------
  `SUPER_ADMIN`      系统管理员
  `EVENT_OPERATOR`   会务运营，可管理场次和报名
  `CHECKIN_STAFF`    现场核验员，可执行授权核验并查看必要信息
  `DATA_OPERATOR`    数据运营，可查看统计

### 12.2 权限码

权限码采用 `resource:action` 格式，例如：

``` text
event:read
event:create
event:update
event:publish
registration:read
checkin:create
checkin:read
statistics:read
user:read
user:assign_role
```

### 12.3 MVP 权限范围

-   MVP 暂采用内置角色和角色分配。
-   MVP 暂不提供自定义角色 CRUD 和复杂数据范围授权。
-   角色与权限的映射由后端维护。
-   前端通过 `/api/v1/admin/me`
    获取当前用户权限，据此控制菜单和按钮显示。
-   前端权限控制只用于界面体验，服务端必须对每个受保护接口进行真实鉴权。

## 13. 数据安全与隐私

-   用户只能查询自己的报名和凭证。
-   运营人员只能在其权限范围内查看报名数据。
-   手机号等个人信息按最小必要原则展示或脱敏。
-   核验员只获取完成核验所必需的参会人信息。
-   管理接口必须在服务端鉴权，不能依赖前端传入的 `userId` 决定数据归属。
-   二维码载荷不得直接包含手机号、邮箱等明文个人信息。
-   日志不记录密码、完整令牌、完整二维码载荷。
-   错误响应不得暴露堆栈、SQL、内部服务地址或敏感数据。

## 14. 前端 API 分层与请求封装

### 14.1 调用分层

前端 API 调用链路统一为：

``` text
页面 / 组件
    ↓
应用 API 模块
    ↓
shared API 工厂
    ↓
Axios 客户端
    ↓
Gateway
    ↓
后端服务
```

职责约定：

-   **页面 / 组件**：负责界面状态和用户交互，不直接发起 Axios 请求。
-   **应用 API 模块**：按业务资源组织 API 方法，不按页面组织。
-   **shared API 工厂**：提供通用请求能力、基础配置和类型约束。
-   **Axios 客户端**：统一处理 Base
    URL、请求头、响应解析、认证和错误拦截。
-   **Gateway**：统一对外接收请求并路由到后端服务。

### 14.2 禁止事项

-   页面不得直接调用 Axios。
-   不得在多个页面重复实现 Token 注入、错误处理和响应解包。
-   不得在页面中分别兼容不同后端的响应包装。
-   不得让页面出现 Mock / Real 特殊分支。
-   API 方法应按业务资源组织，例如
    `eventApi`、`registrationApi`、`authApi`。

### 14.3 统一错误处理

共享请求层应集中处理：

-   网络错误；
-   HTTP 状态码；
-   统一错误响应解析；
-   Token 刷新和登录态失效；
-   `traceId` 的保留与错误提示。

具体业务错误由业务模块根据稳定的错误码处理，不应通过判断中文 `message`
实现。

## 15. Mock 规范

Mock 用于在前后端并行开发时模拟 API 行为，不能形成另一套接口契约。

-   Mock 的路径、HTTP 方法、请求参数和响应结构必须与 OpenAPI 一致。
-   Mock 应覆盖成功、空数据、业务失败和边界状态。
-   Mock 数据应符合真实 DTO 和枚举定义。
-   页面不得出现 Mock / Real 特殊分支。
-   Mock 与真实请求的切换由基础设施层完成。
-   OpenAPI 契约变化时，应同步更新 Mock，避免 Mock 长期滞后于真实接口。

------------------------------------------------------------------------

## 16. 幂等与重复请求保护

-   前端可以在提交期间禁用按钮，降低用户重复点击的概率。
-   报名、核验、支付等关键动作必须由后端实现幂等或重复请求保护。
-   前端防抖、按钮禁用不能替代后端业务约束。
-   重复报名、重复核验等业务冲突应返回稳定的错误码和对应 HTTP 状态码。
-   对并发请求的正确性必须由服务端保证，不能依赖前端请求顺序。

具体幂等实现方式和请求标识机制由后端技术设计确定，并在需要时写入具体接口契约。

------------------------------------------------------------------------

## 17. 契约变更与版本管理

-   OpenAPI 文件是接口结构的唯一机器可读契约源。
-   OpenAPI 变更应与代码变更一起提交 Git 并接受评审。
-   破坏性变更包括删除字段、修改字段类型、改变枚举语义、改变认证要求、改变响应结构等，必须显式评审。
-   新增可选字段通常具有较好的向后兼容性，但前端仍应对未知枚举和可选字段做容错。
-   每次契约变更应更新 OpenAPI 的 `info.version`，或在 Git
    提交中清楚记录变更原因。
-   Apifox 用于导入、查看、Mock 和调试，不应与 Git 中的 OpenAPI
    长期维护两份互不一致的接口定义。
-   修改本文中的跨接口规则时，应检查 OpenAPI、前端共享请求层、Mock
    和后端公共响应实现是否需要同步调整。
