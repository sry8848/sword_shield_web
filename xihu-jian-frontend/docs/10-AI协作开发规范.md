# 10 AI Coding 协作规范

## 1. 目标
让 AI 在既有工程边界内完成任务，避免每次生成代码都引入新架构、重复组件或不一致数据结构。

## 2. 接任务前必须确认
目标用户和业务场景、任务所属 Portal/Admin/Shared、现有实现位置、接口是否定义、是否影响路由权限类型组件、验收标准。信息不足且会改变实现方向时先提问，不得编造业务规则。

## 3. 修改前检查
AI 必须阅读 README、相关规范、OpenAPI、目标模块相邻代码和测试。涉及接口时同时检查类型与 Mock，按 [14 的骨架整改项](14-待确认事项.md#前端骨架后续整改)区分目标与现状。

## 4. 修改边界
- **MUST** MVP 只界定首期业务范围。工程架构、接口契约、权限和质量要求按正式规范执行。
- **MUST** 遵守已确定的架构和技术选型。架构规范与具体业务需求出现真实冲突时，暂停相关修改并报告冲突及出处，等确认后再继续。不得自行改变架构原则、扩大业务范围或为适配现有代码而改写业务需求。
- **MUST** 只实现已授权的实际场景，禁止为展示架构预建演示业务和空目录。根据实际复杂度采用 Feature、组件和 Composable，简单页面禁止机械拆分。拆分依据见 [04 组件开发规范](04-组件开发规范.md)。
- **MUST** 涉及契约变更时遵循 [06 契约变更规则](06-接口与数据规范.md#17-契约变更与版本管理)。禁止提交真实密钥或删除无关业务代码。
- **SHOULD** 优先局部改动并复用已有公共能力，复杂任务先明确实施范围，验证要求按 [09 测试与质量规范](09-测试与质量规范.md)执行。

## 5. AI 交付内容
说明修改文件、业务变化、接口和类型变化、验证方式、未完成事项、风险和后端配合项。无法运行验证时必须明确说明，不得声称通过。

## 6. 提示词模板
```text
请先阅读 README 和相关规范，再检查目标模块现有实现。
本次目标：
业务场景：
涉及应用：Portal / Admin / Shared
接口契约：
验收标准：
约束：遵循已定架构、接口契约和已授权范围。遇到真实冲突先报告。
完成后列出修改文件、验证命令、结果和遗留风险。
```
