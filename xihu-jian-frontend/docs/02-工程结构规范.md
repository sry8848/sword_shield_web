# 02 工程结构规范

## 1. 根目录

`apps/portal` 和 `apps/admin` 为独立应用，`packages/shared` 为共享包。根目录的 `docs`、`openapi` 和 `tests` 分别维护规范、接口契约和端到端测试。

## 2. 应用内部结构

下图是目标结构。Admin 采用同样的组织原则，按后台实际职责划分 Feature。

```text
apps/portal/src/
├── app/            应用启动和依赖装配
├── router/         应用路由和守卫
├── layouts/        应用布局
├── features/       按业务领域组织
│   ├── activity/
│   ├── registration/
│   └── user/
├── components/    应用内跨 Feature 复用的组件
├── stores/        应用级客户端状态
└── styles/        全局样式和设计 Token
```

**MUST** 业务代码归属对应 Feature。应用级目录放应用装配和跨 Feature 的公共能力。业务组件和业务逻辑在所属 Feature 内维护。

**MAY** 复杂 Feature 可按职责组织。简单 Feature 可以直接放少量文件，按实际需要建立子目录。

```text
activity/
├── pages/
├── components/
├── composables/
├── api/
├── model/
└── utils/
```

## 3. 共享包与依赖边界

- **MUST** Portal 和 Admin 只能依赖 Shared 的公共导出。Shared 不依赖任一应用，两应用不相互依赖。共享包的职责见 [01 应用边界](01-技术选型与架构设计.md#4-应用边界)。
- **MUST** 跨 Feature 依赖经过被依赖 Feature 明确公开的接口。API 和纯工具不依赖页面或 UI 组件。
- **SHOULD** 抽取公共能力前核对实际使用方、语义是否稳定及调用是否更简单。出现循环依赖时调整模块边界。
- **MUST** 按实际职责组织代码。业务 API 直接复用共享 HTTP 能力，禁止仅为分层额外建立 Service、Repository 或 Adapter 层。契约与展示模型不一致时，按 [06 的类型规则](06-接口与数据规范.md#53-typescript-类型与生成)转换。

## 4. 命名与导入

| 类型 | 规则 | 示例 |
|---|---|---|
| Vue 页面 | PascalCase | `ActivityListPage.vue` |
| Vue 组件 | PascalCase | `ActivityCard.vue` |
| TS 工具 | camelCase | `formatDate.ts` |
| Store | camelCase | `auth.ts` |
| 类型文件 | 语义命名 | `activity.ts` |
| 测试 | 源文件名 + spec | `activity.spec.ts` |

类型导入使用 `import type`。业务常量放在其所属模块，页面组件只提供视图入口。
