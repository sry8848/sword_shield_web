# 02 工程结构规范

## 1. 根目录
`apps/portal`、`apps/admin`、`packages/shared`、`docs`、`openapi`、`tests`。

## 2. 应用内部结构
```text
src/
  api/             应用 API 客户端实例
  assets/          图片、字体等静态资源
  components/      应用内可复用组件
  composables/     可复用组合式逻辑
  layouts/         页面布局
  mocks/           仅应用特有的 Mock
  pages/           路由页面
  router/          路由配置
  stores/          Pinia Store
  styles/          全局样式和设计 Token
  utils/           应用内通用工具
  App.vue
  main.ts
```
业务复杂后再增加 `features/`，不要初期为形式增加大量空目录。

## 3. 页面与业务模块
- `pages/` 中一个目录对应一个页面或紧密相关的页面组。
- 页面负责组合组件、触发页面级数据加载和管理页面局部状态。
- 页面不直接写 Axios。
- 业务规则优先放在业务 API、composable 或纯函数中。
- 同一业务模块的页面、组件和工具尽量相邻。

## 4. 共享包结构
```text
packages/shared/src/
  api/
  http/
  mocks/
  types/
  utils/
  index.ts
```
共享包只输出稳定、明确的公共 API，不让应用深层引用内部实现。

## 5. 依赖边界
MUST：页面可以依赖应用组件、应用 API、共享包；共享包不得依赖应用；API 层不得依赖页面组件；纯工具不得依赖 UI 组件。
SHOULD：避免跨模块相互引用内部文件；公共能力通过明确导出；循环依赖应调整模块边界。

## 6. 命名
| 类型 | 规则 | 示例 |
|---|---|---|
| Vue 页面 | PascalCase | `ActivityListPage.vue` |
| Vue 组件 | PascalCase | `ActivityCard.vue` |
| TS 工具 | camelCase | `formatDate.ts` |
| Store | camelCase | `auth.ts` |
| 类型文件 | 语义命名 | `activity.ts` |
| 测试 | 源文件名 + spec | `activity.spec.ts` |

## 7. 导入规则
类型导入使用 `import type`；不从页面组件导出业务常量；避免多层目录穿透，必要时调整导出边界。

## 8. 抽取公共模块
同时满足以下条件再考虑抽取：至少两个真实使用场景、语义和输入输出稳定、抽取后调用方更简单。代码相似本身不是抽象理由。
