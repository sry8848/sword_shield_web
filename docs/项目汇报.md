# 项目汇报

## 第一章 选题与背景

### 1.1 选题题目

**基于西湖论剑·数字安全大会品牌宣传用户交互的活动平台**

本项目属于企业服务方向的商业类选题，围绕西湖论剑·数字安全大会的宣传和参会服务，面向参会用户、参展企业及大会运营人员，设计集活动展示、报名、内容浏览、资料下载和互动交流于一体的活动平台。

平台建设以会前、会中、会后的实际使用场景为出发点：会前帮助用户了解大会、选择活动并完成报名；会中方便用户查看议程、获取活动信息和参与交流；会后提供回放、演讲资料和成果内容，让用户在大会结束后仍有访问平台的理由。

### 1.2 业务背景与行业痛点

#### 1.2.1 业务背景

西湖论剑于 2012 年创办，2023 年由“西湖论剑·网络安全大会”升级为“西湖论剑·数字安全大会”。近年来大会讨论的内容逐渐从传统网络安全，扩展到数字化应用中的安全问题，交流形式也涵盖论坛、展览、人才培养和科普活动。

命题以 2024 年第十二届大会为背景。据新华网报道，该届大会于 2024 年 5 月 18 日在杭州国际博览中心举行，重点讨论数据要素产业应用、人工智能与数字安全等议题。这类专业大会既承担行业交流的作用，也为企业展示产品、发布成果和接触潜在合作方提供了机会。

大会的服务对象已经不限于现场参会人员。2020 年大会便采用北京、杭州两地直播间连线的线上峰会形式，设置 1 个主论坛和 6 个分论坛，官网还提供了小程序、直播预约等入口。线上参与因此是大会已有的业务场景。

据对前十一届大会的统计，大会线下参会嘉宾已累计超过 1 万人次，线上直播观看累计超过 2500 万人次。说明平台需要同时考虑现场参会和远程观看两类使用方式。用户可能通过一篇宣传文章认识大会，再进入平台报名或观看直播；后续能否方便地找到回放和资料，会影响他们是否继续关注大会。

#### 1.2.2 行业痛点

**（1）参会环节多，信息与操作需要衔接。**

用户从了解大会到实际参会，需要查找活动时间、地点、议题、嘉宾和报名方式。如果宣传页面、报名入口及议程信息缺少关联，用户就需要反复查找。例如，看到感兴趣的论坛后，还要重新寻找报名入口；完成报名后，又要另行确认活动安排。平台需要围绕具体活动组织信息，让用户能够顺着当前操作完成下一步。

**（2）不同群体关注的内容有差别。**

选题材料列出的受众包括政府机构、科研单位、企业信息安全负责人、媒体等，同时提出吸引学生和相关行业用户的目标。企业用户可能更关心产品方案和应用案例，科研人员更关注技术议题，学生则需要容易理解的活动介绍和学习资料。如果所有内容都按同一种方式排列，新用户就较难判断哪些活动适合自己。活动分类和内容说明需要帮助用户做出选择。

**（3）会后内容仍有价值，但需要方便查找。**

专业大会会产生演讲视频、嘉宾 PPT、技术成果和展商资料。用户可能因为时间冲突错过某场论坛，也可能在工作或学习中再次用到某份材料。如果这些内容没有与对应活动、嘉宾建立清楚的关联，查找和再次使用就会比较麻烦。命题将视频回放、资料下载和成果展示列入要求，正是为了让大会内容在会后继续被使用。

**（4）宣传触达与实际参与之间缺少清楚的对应关系。**

命题明确要求报名来源可追溯，并提供报名人数、参与人数等统计。宣传内容被浏览或分享，并不能直接说明有多少用户最终报名、参与活动。运营人员需要了解用户从哪些渠道进入平台、对哪些活动感兴趣，才能判断后续应重点宣传什么。平台既要支持用户互动，也要为运营复盘保留必要的业务记录。

### 1.3 选题意义

**对参会用户而言，平台可以减少查找和重复操作。** 将活动介绍、报名、议程和会后资料围绕同一场活动组织起来，有助于用户连续完成参会过程。无法到场的用户也可以通过线上内容了解大会；学生和初次接触数字安全领域的用户，则能更方便地找到适合自己的议题和学习材料。

**对大会运营和参展企业而言，平台可以为宣传与服务提供更具体的依据。** 集中维护活动和展商信息，有助于减少多处更新带来的遗漏；记录报名来源及活动参与情况，可以帮助运营人员比较不同渠道的效果。展商的产品介绍、视频和成果资料也能够在会后继续展示，延长用户了解企业的时间。

**对本项目的课程实践而言，选题提供了比较完整的业务过程。** 用户注册、活动报名、内容发布、互动交流和后台统计之间存在明确联系，适合用来开展需求分析、业务建模与系统设计。项目是否有价值，可以落到具体问题上判断：用户能否顺利完成报名，能否找到需要的活动资料，运营人员能否看清报名和参与情况。这也为后续章节的需求梳理与功能设计提供了依据。

## 第二章 需求分析

### 2.1 业务需求

西湖论剑活动平台需要服务于大会宣传、会务组织和会后运营。根据选题要求，平台建设应帮助主办方扩大大会影响力，将宣传带来的关注转化为实际参与，并通过大会内容和交流活动吸引用户持续关注。围绕这些目标，本项目的业务需求主要包括以下五个方面。

#### 2.1.1 支持大会宣传，吸引目标群体参与

大会宣传需要让用户了解大会讨论什么、有哪些活动，以及参加后能够获得什么。面向行业从业者，可以突出技术议题、应用案例和参展企业；面向学生及初次接触大会的用户，则需要把活动内容和学习价值介绍清楚，降低理解门槛。

宣传内容还需要与具体活动衔接。用户通过资讯或分享内容进入平台后，应能继续了解相关活动并找到参与方式，减少从了解大会到报名参会之间的中断。同时，保留报名来源，为后续比较不同宣传渠道的效果提供依据。

#### 2.1.2 配合会务安排，保持参会信息一致

大会涉及多场活动及不同的时间、地点和参与方式，运营人员需要统一维护对外发布的信息，并根据会务安排及时更新。活动安排发生变化时，用户查到的活动介绍、议程和报名信息应保持一致，减少因信息不一致产生的咨询和误解。

报名情况需要按活动汇总，便于主办方掌握各场活动的报名规模，为会务准备提供参考。现场参会和线上观看也应有清楚的说明，让用户根据自身情况选择参与方式。

#### 2.1.3 展示展商与大会成果，方便后续了解

展商展示需要帮助用户了解企业的业务方向、产品和应用情况。因此，企业介绍、产品资料、视频和相关新闻应围绕展商组织，方便感兴趣的用户进一步查阅。

大会发布的技术成果和相关资料也需要集中展示，并说明所属活动或发布单位。这样既方便参会人员回顾，也能让未到场的用户了解大会成果，为展商和成果发布方提供会期之外的展示机会。

#### 2.1.4 保留会后内容，支持用户持续参与

大会结束后，演讲回放、嘉宾 PPT 和成果资料仍有学习与参考价值。平台需要将这些内容与对应活动、嘉宾关联，方便错过直播的用户补看，也方便参会人员再次查阅。

持续运营还需要围绕内容开展交流。通过评论、分享等方式，让用户能够表达看法、交流问题或邀请同行了解相关议题，使会后访问有具体内容可看、有实际问题可讨论。

#### 2.1.5 掌握活动效果，为运营调整提供依据

主办方需要了解哪些活动受到关注、各场活动的报名和参与情况，以及报名用户主要来自哪些渠道。这些信息应能够按活动汇总，帮助运营人员判断宣传重点和内容安排是否符合受众需要。

统计时需要区分报名与实际参与，避免将报名人数直接当作到场人数或观看人数。会后复盘应根据业务过程中记录的数据说明活动效果，为下一阶段的宣传和活动组织提供参考。

### 2.2 用户需求

结合选题中的服务对象，平台的用户需求主要从参会用户和大会运营管理人员两方面展开。参会用户关注能否找到合适的活动、顺利参与并获得所需资料；运营管理人员则需要维护大会信息、组织活动和掌握参与情况。

#### 2.2.1 参会用户需求

**（1）了解大会，选择感兴趣的活动。**

初次访问平台时，用户希望先了解大会主题、举办时间、地点和主要内容，再根据活动介绍判断是否参加。面对多场论坛和专题活动，用户需要看清各场活动的议题、嘉宾和安排，方便选择与自身工作或学习有关的内容。

不同参会群体的关注点有所差别。结合命题中的受众范围，可从以下几个方面组织内容，帮助用户查找和选择。

| 用户群体            | 主要关注内容                   |
| --------------- | ------------------------ |
| 政府机构及企业信息安全相关人员 | 行业议题、安全建设经验、产品方案和应用案例    |
| 科研人员及技术从业者      | 技术报告、专题交流、研究成果和演讲资料      |
| 学生及初次接触数字安全的用户  | 容易理解的活动介绍、适合学习的议题和可回看的内容 |
| 媒体及其他关注大会的用户    | 大会动态、成果发布、图片和视频等公开信息     |

**（2）完成报名，查阅自己的参会记录。**

决定参加活动后，用户需要了解报名条件、报名时间和参与方式，并得到明确的报名结果。遇到重复报名、名额已满等情况时，也希望知道原因。报名后，用户应能查阅自己已报名的活动及相关安排，避免忘记参加了哪场活动。

在使用个人账号的过程中，用户还需要查看和维护昵称、联系方式等个人资料，使账号中的信息与自身情况保持一致。

**（3）根据实际情况参与现场活动或线上观看。**

现场参会人员更关注活动时间、会场位置和议程安排，希望在手机上也能方便地查到这些信息。不能到场的用户则需要找到对应活动的直播入口，了解直播是否开始，以及结束后是否提供回放。对于时间冲突而错过的内容，用户希望之后能够补看。

**（4）获取资料，继续学习和交流。**

观看演讲后，用户可能还需要下载嘉宾 PPT，或再次查找其中提到的成果和案例。因此，资料应有清楚的名称和内容说明，并能与对应活动或嘉宾联系起来，方便用户确认是否为自己需要的材料。

用户也希望围绕活动和资讯表达看法，通过点赞、评论和分享参与交流。分享给同行或同学的内容，应便于接收者找到相关活动介绍和参与方式。

#### 2.2.2 大会运营管理人员需求

**（1）维护活动安排，及时更新对外信息。**

运营管理人员需要录入和修改活动名称、时间、地点及内容介绍，按照会务安排发布活动。活动调整后，需要及时更新相关信息，使用户能够查到当前安排。管理多场活动时，还应便于区分各场活动的状态，减少遗漏或误操作。

**（2）整理宣传内容，管理图片和视频。**

大会宣传会使用资讯、图片和视频等多种内容。运营管理人员需要将这些内容整理后发布，并建立清楚的关联。例如，发布某场论坛的报道时，可以配合现场图片或视频，帮助用户了解活动情况；发现内容有误时，也需要能够及时修正。

**（3）查看活动数据，了解报名与关注情况。**

运营管理人员需要查看各场活动的报名数量、参与情况和关注程度，了解不同活动之间的差异。对于报名来源，也需要能够追溯，以判断哪些宣传渠道带来了实际报名。查看统计结果时，应能明确数据对应的活动及统计含义，便于会务准备和会后复盘。

### 2.3 系统需求

根据前面的业务需求和用户需求，系统需要提供活动展示、报名、内容管理和互动等能力，并保证操作结果准确、信息查阅方便。具体要求分为功能需求、质量要求以及运行约束三个方面。

#### 2.3.1 功能需求

| 功能范围     | 系统要求                                                      |
| -------- | --------------------------------------------------------- |
| 账号与个人信息  | 支持用户注册、登录及个人资料维护，提供个人报名记录查询；管理员通过管理入口登录，执行相应管理操作。         |
| 活动信息     | 展示活动名称、时间、地点、内容、嘉宾及参与方式，支持活动订阅；管理端能够维护活动信息，并控制发布状态。       |
| 活动报名     | 记录用户与所报名活动的对应关系、报名时间和来源渠道；根据报名条件受理申请，对重复报名、名额已满等情况给出明确提示。 |
| 直播、回放与资料 | 提供对应活动的直播和回放入口，展示资料名称、说明及下载入口，使用户能够按活动或嘉宾找到所需内容。          |
| 展商与成果展示  | 展示展商介绍、产品、视频及相关新闻，集中呈现大会成果，并标明相关企业、发布单位或所属活动。             |
| 资讯与互动    | 支持资讯、图片和视频内容的发布与浏览，建立内容之间的关联；提供点赞、评论和分享等互动方式。             |
| 活动统计     | 按活动汇总报名及参与情况，保留来源渠道信息，为活动管理和运营复盘提供依据。                     |

报名记录应能够关联到明确的用户和活动。同一用户对同一活动的重复提交不能产生多条有效报名，活动设置人数上限后，受理结果也应符合该限制。涉及时间、名额等条件时，页面说明与系统判断应保持一致。

统计结果应来自对应的业务记录，并明确统计对象。报名数量、实际参与数量和内容浏览情况分别反映不同的行为，应按各自口径展示，便于运营人员理解和比较。

#### 2.3.2 质量要求

**（1）权限与信息安全。**

系统应区分普通用户和管理员的操作权限。用户只能维护自己的个人资料、查询自己的报名记录；活动发布和管理操作应由具备权限的管理员执行。权限检查应覆盖实际的数据访问和修改操作。账号密码应以安全的方式保存，个人联系方式等信息应限制访问范围。

**（2）操作清楚，结果明确。**

活动介绍、报名入口、直播入口和资料下载入口应便于查找。表单需要说明必填内容，对输入不完整或不符合要求的情况给出具体提示。报名、信息修改和内容发布等操作完成后，应显示明确结果；处理失败时，应说明原因，避免用户误以为操作已经成功。

**（3）数据准确，处理结果一致。**

活动信息调整后，列表与详情中展示的内容应保持一致。多人同时报名或重复提交时，系统应正确处理报名记录和名额，避免重复计数或超出限制。操作中断或保存失败时，不应留下被误认为已经完成的记录。

**（4）满足日常访问和集中使用需要。**

系统应支持用户同时浏览和报名。内容较多或图片、视频正在加载时，应有清楚的加载状态，避免用户因长时间没有反馈而反复操作。后续测试需要记录主要页面和报名操作的响应情况，检查集中使用时是否出现请求失败、重复记录或统计不一致等问题。

#### 2.3.3 运行环境与约束

系统应支持 PC 和主流移动设备访问。在手机上，活动信息、表单和操作按钮应能够正常显示和使用；图片与视频内容应随页面宽度调整，减少横向滚动和文字遮挡。

项目拟采用 Java 17、Spring Boot 和 Vue 3 开展开发，使用 MySQL 保存业务数据，并配合 Redis、MinIO 等组件支持数据缓存与文件存储。

平台拟通过 Web 应用提供服务，同时考虑 PC 与手机浏览器的使用体验。小程序端的建设范围需结合命题要求和开发安排确定。

## 第三章 角色与业务流程

### 3.1 系统涉及的角色划分

结合前面的用户需求，系统拟按访问身份和操作职责划分为游客、注册用户和管理员三类角色。其中，游客表示未登录时的访问状态，注册用户通过个人账号参与活动，管理员承担大会运营管理工作。

| 角色   | 身份说明              | 主要操作范围                                    |
| ---- | ----------------- | ----------------------------------------- |
| 游客   | 尚未注册或暂未登录的访问者     | 浏览大会及活动信息，查看资讯、展商和大会成果，进行注册或登录。           |
| 注册用户 | 已完成注册并登录的个人用户     | 浏览公开内容、报名活动、查阅个人报名记录、维护个人资料，以及参与点赞、评论和分享。 |
| 管理员  | 使用管理账号登录的大会运营管理人员 | 维护活动信息及发布状态，管理图片和视频内容，查看活动统计数据。           |

#### 3.1.1 游客

游客主要通过公开内容了解大会，判断是否有感兴趣的活动。因此，游客能够浏览活动介绍、资讯、展商及成果等信息，先了解大会再决定是否参与。进入需要关联个人身份的报名或互动操作时，应引导其注册或登录。

#### 3.1.2 注册用户

注册用户在浏览公开内容的基础上，可以报名活动、查看自己的报名记录，并维护昵称、联系方式等个人资料。参与评论、点赞和分享时，相关行为与其账号关联，便于记录个人参与情况。

注册用户只能维护本人的个人资料和相关记录，不能修改大会活动、其他用户资料或后台发布内容。用户登录后仍需遵守各场活动的报名条件，注册身份本身不代表已经获得某场活动的参与资格。

#### 3.1.3 管理员

管理员对应前文的大会运营管理人员，主要负责维护活动安排和对外发布的信息。通过管理入口登录后，管理员可以新增、修改活动信息，调整发布状态，并整理、发布大会图片和视频。管理员还需要查看活动数量、报名数量及热度等统计，掌握活动开展情况。

管理员账号与普通用户账号分别承担后台管理和个人参会职责。普通用户登录后不能直接获得管理权限；管理员如果以个人身份报名参会，应通过普通用户入口完成相应操作。

#### 3.1.4 角色与受众群体的关系

学生、科研人员、企业信息安全人员和媒体等属于不同的受众群体，其差别主要体现在关注的内容和参与目的上。在系统中，这些群体均可根据是否登录，以游客或注册用户身份使用平台，后续用例图统一采用相应角色名称。

本次设计将嘉宾和展商作为活动介绍、企业展示及成果资料的关联对象，相关内容由管理员统一维护，不单独设置嘉宾或展商管理角色。

#### 3.2.1 活动创建与发布流程

活动创建与发布拟按以下流程开展：管理员登录后填写活动标题、起止时间等信息，系统检查必填内容，缺少内容时提示补充。提交后，系统核对管理权限及活动信息，符合要求时保存并发布活动，建立初始统计数据。发布成功后更新活动列表，供用户浏览和选择。

#### 3.2.2 用户报名活动流程

报名流程拟从用户选择活动开始。用户发起报名时，系统先检查登录状态，未登录则引导登录。登录后提交活动信息及报名来源，系统依次检查活动是否存在、报名是否已截止、是否尚未开放报名、是否重复报名，以及报名人数是否达到上限。检查通过后，保存用户、活动、来源渠道和报名时间，反馈报名结果。

#### 3.2.3 资料下载链接获取流程

## 第四章 功能与用例

### 4.1 功能模块清单

平台拟围绕大会宣传、活动参与、内容查阅和运营管理规划功能，按业务划分为账号与个人信息、活动服务、内容展示、互动与运营四个部分。使用角色沿用游客、注册用户和管理员的划分，各模块的具体功能如下。

| 直播与回放  | 直播观看      | 游客、注册用户  | 在活动详情中查看直播入口，进入对应活动的直播内容。                 |
