## 1. 背景、目标与范围

阶段二已交付账号与角色的数据迁移、开发和测试账号，以及 Argon2id 密码编码能力。阶段三让已启用的账号能用手机号和密码登录 Portal，访问需要身份的页面，刷新或重新打开应用后恢复有效会话，使用期间自动续期，并能退出当前会话。公开页面继续允许游客访问。

| 范围 | 交付内容 |
| --- | --- |
| 阶段三 | Portal 登录页、登录限流、当前身份、会话建立和续期、JWT 签发与资源服务验证、JWKS、会话恢复、后端处理多标签页并发刷新、退出及私有状态清理。通过 Gateway 验证 Portal 链路，并独立验收 Activity 的认证边界。 |
| 阶段四 | Admin 登录与独立会话、`SUPER_ADMIN` 准入、Redis 在线状态校验、Outbox，以及 Admin 撤权的 5 秒目标。 |
| 阶段五 | 两端整体验收、跨应用会话隔离联调、安全审计补齐和故障恢复验证。 |
| 后续业务模块 | 注册、短信校验、密码管理、MFA、账号管理界面、后台角色管理、细粒度 RBAC 和设备管理。 |

Portal 和 Admin 共用账号。阶段三交付阶段四会用到的账号验密、JWT、会话轮换和前端刷新能力，并保留应用级隔离。依据[技术评审第 11.2、12 节](登录与会话模块技术评审_2026-11-10_19-17.md#112-阶段与完成条件)和[阶段二账号需求](账号基础数据与初始账号需求_2026-11-11_09-01.md)。

## 2. 主用例与功能需求

### 2.1 主用例

**参与者**为具有启用账号的参会用户。用户打开 Portal 并进入受保护页面时，系统先尝试恢复当前浏览器的会话。有有效会话时直接进入目标页面。没有有效会话时，用户通过登录页提交手机号和密码，登录成功后回到经过校验的站内目标页面。用户在使用期间由系统续期，主动退出后回到未登录状态。其他设备可继续使用自己的会话。

### 2.2 功能需求

| 编号 | 需求 |
| --- | --- |
| P3-FR-01 | **登录与失败反馈。** Portal 提供手机号、密码输入和提交反馈。Identity 接受符合契约的中国大陆 11 位手机号和非空密码，复用已有账号和 Argon2id 验密能力。已启用且凭证正确的账号可以登录，后台角色不参与 Portal 准入。格式错误返回参数错误。未知手机号、错误密码、禁用账号统一返回 `401 UNAUTHENTICATED`，均不得建立会话或下发凭证。未知手机号也执行一次虚拟密码哈希验证。 |
| P3-FR-02 | **登录限流。** 按手机号和来源 IP 分别限制登录尝试频率。达到限制后的请求返回 `429 TOO_MANY_REQUESTS`，且不得创建会话。限制窗口结束后允许再次尝试。限流使用 Redis，具体参数通过测试确定。 |
| P3-FR-03 | **建立会话。** 登录成功时，Identity 在 MySQL 建立归属于该账号的独立 Portal 会话并保存首个 Refresh Token 哈希。会话和凭证持久化成功后才返回 Access Token 并设置 Refresh Cookie。已有设备的会话保持有效。 |
| P3-FR-04 | **当前身份与访问控制。** Portal 使用 Bearer Access Token 调用 `me` 和受保护接口。Identity 和 Activity 校验 JWT 的签名、签发者、Portal 受众、过期时间及应用类型，从已验证的凭证识别账号。Activity 通过 Gateway 和直连时都执行校验。`me` 返回当前账号的 `id` 与 `maskedPhone`。受保护请求的 Portal JWT 校验不查询 Redis 在线状态。 |
| P3-FR-05 | **服务端续期。** Identity 根据 Portal Refresh Cookie 识别所属会话，检查应用、账号和会话状态，再处理凭证有效性与轮换。有效且未消费的 Refresh Token 只能成功消费一次，消费与写入唯一后继在同一事务完成。首次轮换返回新的 Access Token，并通过 Cookie 更新 Refresh Token。空闲期限从成功登录或最近一次成功轮换起算，绝对期限从会话创建时起算。任一会话期限届满、账号禁用、凭证版本失效、会话撤销或凭证无效时，拒绝续期。 |
| P3-FR-06 | **重复刷新与重放。** 账号与会话仍有效时，对已经成功轮换的旧凭证按第 3.2 节处理。宽限期内返回 `200` 和新的 Access Token，省略 `Set-Cookie`，保留已写入的后继与会话期限。超期重放撤销该凭证所属会话，记录安全审计，其他会话保持有效。 |
| P3-FR-07 | **浏览器恢复与自动续期。** 刷新页面或重新打开 Portal 后，前端通过浏览器携带的有效 Refresh Cookie 恢复会话，并通过 `me` 读取当前身份。受保护路由等待恢复结果再判断是否放行。收到 `401 ACCESS_TOKEN_EXPIRED` 时在单实例内合并并发刷新。续期返回的账号与原请求所属账号一致时，更新 Access Token 并最多重试原请求一次。返回其他账号时清理本地旧状态并终止原请求。认证接口自身的错误不递归刷新，普通业务 `403 FORBIDDEN` 保留登录态。确认刷新凭证失效时，清理当前会话并提示重新登录。 |
| P3-FR-08 | **多标签页续期。** 标签页可携带同一 Portal Refresh Cookie 并发刷新，各自处理成功响应、保存内存 Access Token 并继续原请求。由服务端保证同一旧凭证只有一个轮换后继，浏览器处理首次轮换的 `Set-Cookie`。Portal 前端无需跨标签页互斥、广播或等待协调。 |
| P3-FR-09 | **主动退出与旧状态清理。** 退出成功前，Identity 撤销当前 Portal 会话及其续期资格，并清除对应 Refresh Cookie。发起退出或切换账号的标签页清除旧身份、内存 Access Token 和私有查询缓存，取消旧在途查询并丢弃旧响应。其他标签页在后续续期失败时清理自己的状态。主动退出只影响当前会话，已签发的 Access Token 保留原剩余有效期，至多 600 秒。 |
| P3-FR-10 | **账号禁用。** 账号禁用后，拒绝其新登录和所有 Portal 会话的续期。已签发的 Access Token 按原过期时间失效，剩余有效期至多 600 秒。账号重新启用后可新建会话，此次禁用导致失效的旧会话不能恢复。验收通过受控测试数据触发账号状态变化。 |

依据[当前业务设计第 5～8 节](../../设计/登录设计/登录设计_2026-11-25_10-40.md)、[技术设计第 2～4 节](../../设计/登录设计/登录与会话技术设计_2026-11-25_10-40.md)及前端[路由与权限规范](../../../xihu-jian-frontend/docs/05-路由与权限规范.md)、[接口与数据规范](../../../xihu-jian-frontend/docs/06-接口与数据规范.md#8-身份认证与-token-刷新)、[状态管理规范](../../../xihu-jian-frontend/docs/08-状态管理规范.md)。

## 3. 接口与会话边界

### 3.1 接口摘要

字段、响应和错误语义以现行认证契约为准。下表使用经过 Gateway 的完整路径。[OpenAPI](../../../xihu-jian-frontend/openapi/openapi.yaml)

| 操作 | 接口 | 凭证与结果 |
| --- | --- | --- |
| 登录 | `POST /api/v1/auth/portal/login` | 请求体为 `phone`、`password`。成功返回 `AuthSession` 并设置 Portal Refresh Cookie。 |
| 刷新 | `POST /api/v1/auth/portal/refresh` | 由浏览器携带 Portal Refresh Cookie。成功返回 `AuthSession`。首次轮换设置新 Cookie，宽限期内的重复请求省略 `Set-Cookie`。 |
| 退出 | `POST /api/v1/auth/portal/logout` | 由浏览器携带 Portal Refresh Cookie。成功返回 `loggedOut: true` 并清除 Cookie。 |
| 当前身份 | `GET /api/v1/auth/portal/me` | 使用 Portal Bearer Access Token，返回 `UserProfile`，字段为 `id`、`maskedPhone`。 |
| 公钥 | `GET /api/v1/auth/jwks` | 公开发布验签公钥集合，供 Identity 以外的资源服务验签。 |

`AuthSession` 包含 `accessToken`、`tokenType`、`expiresIn` 和 `user`，其中 `expiresIn` 固定为 600 秒，`user` 使用 `UserProfile`。刷新和退出以 Refresh Cookie 作为认证凭证，无需 Bearer 或请求体。凭证缺失、无效或已过期时，按各接口的 `401` 契约处理。

### 3.2 已消费 Refresh Token 判定表

时差从服务端首次成功轮换的事务提交时刻起算。这张表适用于账号和会话仍有效的情形。账号已禁用、会话到期或撤销时，按无效会话处理。

| 时差 | 服务端结果 | 会话及凭证变化 |
| --- | --- | --- |
| ≤ 10 秒，含恰好 10 秒 | `200 AuthSession` | 签发新的 Access Token。省略 `Set-Cookie`，保留唯一后继和原空闲、绝对期限，宽限期保持原值。 |
| > 10 秒 | `401 REFRESH_TOKEN_REPLAYED` | 撤销所属会话及其 Refresh Token，后继 Refresh Token 也不能续期。该会话已经签发的 Access Token 按原到期时间失效。 |

## 4. 安全与工程约束

| 编号 | 约束 |
| --- | --- |
| P3-NFR-01 | Access Token 使用 RS256，`exp` 与 `iat` 相差 600 秒。签名私钥通过服务端外置配置管理，JWKS 仅发布公钥，前端仅在内存保留 Access Token。Refresh Token 使用 256 bit 安全随机数生成，MySQL 仅保存 SHA-256 哈希及轮换记录。密码、原始令牌和私钥不写入日志。 |
| P3-NFR-02 | Refresh Token 空闲期限 7 天、绝对期限 30 天，续期不可越过绝对期限。`portal_refresh_token` 由浏览器管理，设置 `HttpOnly`，生产环境启用 `Secure`，默认 `SameSite=Lax`，省略 `Domain`，`Path=/api/v1/auth/portal`。清除 Cookie 使用相同名称和路径。登录、刷新、退出校验浏览器请求来源，跨源凭证请求只允许明确授权的来源。 |
| P3-NFR-03 | Identity 使用 Flyway 管理会话和刷新凭证的新增迁移。登录或轮换持久化失败时回滚相关状态，不下发未生效凭证。认证成功响应按 OpenAPI 使用统一成功包结构，JWKS 使用公钥集合结构。认证、授权及 Gateway 错误使用 `application/problem+json`，`traceId` 来自实际请求追踪上下文。 |

依据[技术评审第 4.7、5、8 节](登录与会话模块技术评审_2026-11-10_19-17.md)、[技术设计第 1～4 节](../../设计/登录设计/登录与会话技术设计_2026-11-25_10-40.md)及 [OpenAPI](../../../xihu-jian-frontend/openapi/openapi.yaml)。

## 6. 需求核对与实施决定

下表记录需求评审提出的问题和核对依据。Portal 宽限期与联调配置依现行技术评审和开发计划执行。[阶段三技术评审第 2 节](阶段三Portal登录与会话技术评审_2026-11-23_11-58.md#2-阶段三待确认事项的决定)、[阶段三开发计划](阶段三Portal登录与会话开发计划_2026-11-23_11-58.md)

| 事项 | 已核实的依据和评审提出的问题 |
| --- | --- |
| Portal 退出与访问令牌 | 退出撤销当前会话的 Refresh Token。已签发的 Portal JWT 保留原剩余有效期。当前身份的账号字段以 OpenAPI 的 `id` 为准。 |
| 阶段二前置缺口 | 技术评审第 7、11.2 节将 Redis 连通和 Gateway 路由列为阶段二工作，第 7 节还要求 Activity 直连保护。当前基线已有账号迁移和密码编码，仓库尚未接入 Gateway 业务路由、Identity 登录限流和 Activity JWT 校验。开发分工前需确认阶段二遗留项的承接方式。阶段三仍须通过 Gateway 联调及 Activity 直连验收。 |
| 登录限流与刷新 | 登录按手机号和来源 IP 限流，参数见阶段三技术评审第 2 节。3.3 取消 Portal 刷新的独立 Redis 配额及其对应的测试，OpenAPI 移除该接口的 `429` 声明。 |
| Activity 验收入口 | 当前 Activity 骨架只有启动入口，现有 OpenAPI 中另有报名等需要 Portal Bearer 的业务接口。需确认用于验收服务端认证边界的具体入口。新增业务功能应按对应模块的需求单独交付。 |
| 多标签页续期取舍 | 2026-11-25 采用后端 10 秒宽限期。窗口内旧凭证仍可兑换短期 Access Token，重复请求不会取得后继 Refresh Token。决策及风险见[现行技术设计](../../设计/登录设计/登录与会话技术设计_2026-11-25_10-40.md#41-portal)。 |
