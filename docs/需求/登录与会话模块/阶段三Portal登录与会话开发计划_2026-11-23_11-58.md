# 阶段三 · Portal 登录与会话开发计划

阶段三分为五个可单独验收的任务。普通账号先在真实 Portal 登录并打开受保护的身份页。会话续期、退出和 Activity 验签在此基础上接入。2026-11-25 取消原 3.5 的 Portal 前端协调，双标签页场景由 3.4 验收。保留 Activity 原任务编号 3.6。[阶段三需求](阶段三Portal登录与会话需求_2026-11-23_11-15.md)、[阶段三技术评审](阶段三Portal登录与会话技术评审_2026-11-23_11-58.md)

## 2. 任务卡

### 3.1 环境联通

先写或复用最小验证，再补齐所需配置。

1. 用阶段二的配置验证 Identity 对测试库执行迁移、普通测试账号存在。验证同一开发环境可访问真实 Redis。
2. 复用现有 Gateway/WebFlux 追踪设置和 Portal 的 Vite `/api` 代理。认证路由随 Identity 实际入口接入。联通检查可使用测试处理器或现有健康接口。
3. 验证 Gateway 发到 Identity 的请求能关联同一次请求追踪，以及上游连接异常和超时按已有规范返回 Problem Details。

**完成条件。** 从开发环境能复现 Portal 代理到 Gateway、Gateway 到 Identity、Identity 到 MySQL 和 Redis 的链路。故障验证覆盖 `P3-AC-11` 的 Gateway 部分。先完成联通再开始业务认证，避免把网络故障混入登录排查。

### 3.2 登录与当前身份

1. **后端小步。** 先写登录成功、凭证失败及两维限流测试。实现会话及刷新凭证的 Flyway 迁移、Identity 验密、Redis 限流、登录、JWKS 和 `me`。验证 `me` 在缺失、无效或过期的 Bearer 下返回契约错误。
2. **前端小步。** Portal 通过真实登录和 `me` 接入登录页、内存状态、受保护身份页和站内回跳。复用 Shared HTTP Client 的 Bearer 注入，补齐 Problem Details 读取。通过浏览器验证从访客打开公开页，到登录后显示账号身份。

**完成条件。** 普通测试账号从 Portal 访问受保护身份页，数据库能查到对应会话和首个刷新凭证哈希。跑通 `P3-AC-01`、`P3-AC-02`、`P3-AC-03`。单独验证 `600` 秒 Access Token、Cookie 属性和公开 JWKS。本批在开发或测试环境验收，会话恢复与退出由后续批次接入。

### 3.3 服务端会话生命周期

1. 先用真实 MySQL 验证并发轮换、UTC 消费时间及回滚。按技术评审实现刷新事务、唯一后继、空闲和绝对期限。验证同一旧凭证在首次成功轮换记录的消费时间起 10 秒内（含 10 秒）返回 `200` 和新 Access Token，且省略 `Set-Cookie`。超过窗口按重放撤销所属会话。
2. 实现当前 Portal 会话退出及 Cookie 清除。验证一个设备退出后，另一个设备仍可刷新。禁用和重新启用通过受控测试数据更新账号状态及凭证版本。
3. 验证刷新接口拒绝不可信来源，且失败时不下发 Cookie。覆盖登录、刷新、退出和认证过滤链的 Problem Details 与请求追踪。

**完成条件。** 真实 MySQL 集成测试覆盖 `P3-AC-06`、`P3-AC-07`、`P3-AC-10`，完成 `P3-AC-09` 的服务端部分及 `P3-AC-11` 的认证接口部分。一次成功轮换最多产生一个后继，且退出与重放撤销只影响目标会话。

### 3.4 Portal 会话闭环

1. 先在真实服务上编写一个浏览器用例，覆盖登录、刷新页面恢复、Access Token 到期后续期及主动退出。
2. 接入应用初始化、路由等待和 `me`，使用 Shared 的单实例刷新合并与一次重试。鉴别刷新凭证失效、业务 `403` 和可重试服务错误。
3. 退出、会话失效或切换账号时清理当前标签页的身份和私有缓存，取消旧会话在途的私有请求，并验证人工延迟的旧请求结果。共享 Cookie 换成其他账号后，续期发现账号不同即终止旧请求。
4. 用真实浏览器验证两个标签页携带同一旧 Cookie 并发恢复和续期。每个标签页独立处理自己的响应，确认只有首次轮换响应更新 Cookie，两个标签页随后都可继续请求。

**完成条件。** `P3-AC-05`、`P3-AC-08` 和 `P3-AC-09` 的前端部分通过。用户可从打开 Portal、登录、重开恢复、自动续期到主动退出。退出或切换账号后，发起操作的标签页不会因旧响应恢复旧登录态。

### 3.6 Activity 独立验签

1. 在 Activity 测试源码提供匹配 `GET /api/v1/me/registrations` 的最小处理器，在测试环境通过 Gateway 转发该入口。
2. 接入生产的 Activity Resource Server 安全配置，通过 Identity JWKS 独立验签。在同一测试中验证 Activity 直连与经 Gateway 的请求，覆盖有效、缺失、签名无效、错误签发者、错误受众和到期 JWT。
3. 核对打包产物。测试处理器和测试路由只用于验收，生产构建仅包含 Activity 安全配置。

**完成条件。** `P3-AC-04` 通过，且在 Redis 不可用时，已签发的有效 Portal JWT 仍可通过 Activity 认证。测试入口无报名私有数据。

## 3. 阶段三交付验收

- 后端沿用 Maven 和现有测试配置。真实基础设施测试提供对应的环境配置并确认测试确实执行。用真实 MySQL 验证会话轮换和事务，用真实 Redis 验证登录限流。
- 前端沿用仓库已有 pnpm、Vitest 和 Playwright。第一次接入前端前，按既有规范用 pnpm 10 生成并提交前端锁文件，随后使用冻结安装。涉及前端的任务跑 Lint、Typecheck、Test 和 Build，受影响的用户流程通过 Playwright 验证。测试记录 HTTP 状态、轮换次数、Cookie 变化和会话归属，隐藏原始凭证。
- 回归需求 `P3-AC-01` 至 `P3-AC-11`，保留各批次的验收结果。首次交付前，再从真实 Portal 经 Gateway 跑一遍登录、页面恢复、双标签页续期、退出和 Activity 直连认证。
- 阶段四仅复用账号验密与必要基础设施；Admin 采用纯 Redis Session + Gateway ForwardAuth，按[现行技术设计](../../设计/登录设计/登录与会话技术设计_2026-11-25_10-40.md)另行验收，不复用 Portal JWT/JWKS、会话轮换或刷新协调。阶段三 Portal 计划不变。
