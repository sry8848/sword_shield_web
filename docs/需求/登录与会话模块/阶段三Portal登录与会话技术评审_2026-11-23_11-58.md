## 3. 关键实现取舍

### 3.1 登录、签发与接口保护

认证服务沿用已有账号表和编码器。成功登录在一个 MySQL 事务内写 Portal 会话与首个刷新凭证哈希，提交成功后才发送 Access Token 和 Cookie。两张新表由 Flyway 迁移管理。会话标识、账号标识、应用类型和凭证版本提供后续刷新校验所需的信息。

Identity 和 Activity 使用 Spring Security Resource Server 校验签名、签发者、受众、到期时间和应用类型。Identity 对外发布 JWKS，资源服务配置固定的 JWKS 地址和期望的签发者，避免将 localhost 或服务内地址混入生产 JWT。Identity 的 `me` 与 Activity 都从已验证的 JWT 获取当前身份。Gateway 处理转发与请求上下文，受保护资源的认证由服务自身执行。

按当前部署约定使用同源入口，保留 Portal Cookie 的 `Path=/api/v1/auth/portal` 和 `HttpOnly`，生产启用 `Secure`。签发的 Cookie 带持久化有效期，最长到当前空闲期限与绝对期限中较早的一项，支持重新打开浏览器恢复。登录、刷新和退出在认证入口校验请求来源。成功响应和 Problem Details 沿用 OpenAPI，并复用现有追踪能力。Gateway 路由错误与上游故障按已有工程规范处理。[前端部署规范](../../../xihu-jian-frontend/docs/11-开发与部署规范.md)、[后端工程规范](../../../xihu-backend-complete-scaffold-v0.2/xihu-backend-blueprint/docs/02-工程与编码规范.md)

### 3.2 轮换、退出和禁用

轮换和退出围绕单个数据库会话串行更新。刷新先校验应用、账号状态、账号凭证版本与会话是否有效，再检查旧凭证。在同一事务消费旧 Refresh Token、保存唯一后继并更新空闲期限。消费历史至少保留到所属会话的绝对期限，使服务端能在会话存续期间识别旧凭证再次提交。会话绝对期限固定为创建后 30 天。账号安全状态变化按账号建模约定递增凭证版本，因此重新启用后，旧会话仍不可刷新。[账号数据建模](../../设计/登录设计/账号基础数据建模/账号基础数据建模_2026-11-22_16-20.md)

10 秒宽限期内，重复请求只签发新的 Access Token，当前会话、唯一后继凭证与各期限保持原值。宽限期外重放则先提交对所属会话的撤销及安全审计记录，再返回 `401 REFRESH_TOKEN_REPLAYED`。退出成功也以撤销提交为前提。宽限期从首次成功轮换的提交时刻起算。开发批次先用真实 MySQL 验证并发和提交时间取值。若只能取得事务内写入时间，应在实现评审中比较两种时间并报告差异，保持契约的计时口径直到结论得到确认。

Portal 的无状态 Access Token 在退出、重放撤销或禁用后仍可用到原到期时间。此取舍让 Portal 资源服务验签时只依赖公钥和 JWT 自身。Redis 限流与资源服务验签故障边界可分别测试。

### 3.3 浏览器恢复与并发

Portal 标签页可各自请求刷新并处理返回的 `200`。浏览器使用实际轮换响应写入共享的 Refresh Cookie，各标签页在内存保存自己的 Access Token。Shared 保留每个 HTTP 实例内的刷新合并和原请求至多一次重试。Portal 前端不引入跨标签页锁、广播和等待流程，双标签页场景在 3.4 验收。

退出或切换账号时，发起操作的标签页清理旧私有数据并丢弃旧请求迟到的响应。其他标签页在后续续期失败时清理各自状态。刷新遇到 `429` 或服务故障时提示稍后尝试，确认刷新凭证失效时按会话失效处理。[前端认证规范](../../../xihu-jian-frontend/docs/06-接口与数据规范.md#8-身份认证与-token-刷新)、[前端状态管理规范](../../../xihu-jian-frontend/docs/08-状态管理规范.md)

## 4. 主要验证风险

| 风险 | 验证要求 |
| --- | --- |
| 限流前已执行高开销验密 | 在真实 Redis 上验证两个登录维度独立生效，测试耗尽配额时不会走 Argon2id 或创建会话。 |
| 轮换并发、事务回滚或提交计时偏差 | 使用真实 MySQL、受控时间和并发请求验证唯一后继、10 秒边界、重复成功后期限保持原值、回滚后原凭证有效性以及窗口外只撤销所属会话。 |
| Cookie 写入顺序与响应丢失 | 双标签页测试验证只由首次轮换写 Cookie，重复响应的位置和先后顺序均不覆盖后继。首次响应丢失时，重复响应只能恢复 Access Token，后续可能需要重新登录。 |
| 宽限期内旧凭证仍可兑换 Access Token | 服务端仍执行来源、限流、账号、应用、凭证版本与会话状态检查。窗口不会因重复请求延长。风险与取舍已写入[现行技术设计](../../设计/登录设计/登录与会话技术设计_2026-11-25_10-40.md#41-portal)。 |
| Gateway 可用但 Activity 直连漏验 | 同一组 JWT 在直接和代理入口分别验证。测试入口使用真实 Activity 安全配置，并验证其未打包进生产产物。 |
