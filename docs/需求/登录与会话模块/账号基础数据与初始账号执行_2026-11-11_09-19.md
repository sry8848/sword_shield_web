# 账号基础数据与初始账号执行

本次交付 Identity 的三张基础表、分环境数据库配置、开发与测试账号种子数据、生产超级管理员预置 SQL，以及对应验证。

依据 [需求 1](账号基础数据与初始账号需求_2026-11-11_09-01.md)和[后端工程规范](../../../xihu-backend-complete-scaffold-v0.2/xihu-backend-blueprint/docs/02-工程与编码规范.md#数据访问与迁移)。以下路径均相对 `xihu-backend-complete-scaffold-v0.2/xihu-backend-blueprint/backend/`。

## 1. 先写验证

在 `identity-service/src/test/java/com/swordshield/next/identity/` 新增 `IdentityAccountDataTest.java`，沿用 JUnit 5、AssertJ 和 Spring Boot Test，通过 JDBC 查询真实 MySQL 8。连接使用 `test` Profile 的环境变量，测试数据库由执行人员提前创建。

先写以下断言，再添加依赖和实现，按步骤运行至通过。

| 验证 | 断言 |
| --- | --- |
| 测试账号 | 查到两条种子账号，均为 `ENABLED`，普通账号无后台角色，管理员关联 `SUPER_ADMIN`。 |
| 密码 | 两个哈希均以 `$argon2id$` 开头，使用 `Argon2PasswordEncoder.matches` 验证约定测试密码成功、错误密码失败。 |
| 手机号唯一 | 插入已有手机号触发数据库唯一约束错误。测试事务结束后回滚。 |
| 迁移重复运行 | 再次执行正式迁移与种子迁移，账号数量及已有密码哈希保持一致。 |

另用三个独立的本地验证数据库分别运行 `dev`、`test`、`prod` 配置，检查数据库连接目标及加载范围。`prod` 验证库正式迁移后只有角色定义，账号和账号角色关联均为空。执行生产预置 SQL 的本地副本后，只有指定管理员及其关联。此项使用本地验证数据完成。

现有 `IdentityMvcErrorsTest` 激活了 `test` Profile，接入数据源后同样需要上述测试数据库连接。保留原有 HTTP、异常和追踪断言。

## 2. 添加当前步骤所需依赖

在 `identity-service/pom.xml` 增加以下依赖，保留已有依赖。

- `org.springframework.boot:spring-boot-starter-jdbc`
- `org.springframework.boot:spring-boot-starter-flyway`
- `org.flywaydb:flyway-mysql`
- `com.mysql:mysql-connector-j`，使用 `runtime` scope。
- `org.springframework.security:spring-security-crypto`
- `org.bouncycastle:bcprov-jdk18on`

优先采用现有 Spring Boot 父 POM 管理的版本。未被管理的依赖在 POM 中固定兼容版本。当前步骤使用 JDBC 完成数据库验证，业务持久化类随登录用例接入。

Spring Boot 4 的 Flyway 接入和 MySQL 模块依据[官方数据库初始化文档](https://docs.spring.io/spring-boot/how-to/data-initialization.html)。

## 3. 新增正式迁移

新增 `identity-service/src/main/resources/db/migration/V1__create_identity_accounts.sql`，使用 InnoDB 和 `utf8mb4`，按以下定义建表。

| 表 | 列与约束 |
| --- | --- |
| `identity_account` | `id BIGINT AUTO_INCREMENT PRIMARY KEY`，`phone VARCHAR(11) NOT NULL` 并建立唯一约束 `uk_identity_account_phone`，`password_hash VARCHAR(255) NOT NULL`，`status VARCHAR(16) NOT NULL`，`credential_version INT NOT NULL DEFAULT 1`，`permission_version INT NOT NULL DEFAULT 1`。 |
| `identity_role` | `id BIGINT AUTO_INCREMENT PRIMARY KEY`，`code VARCHAR(64) NOT NULL` 并建立唯一约束 `uk_identity_role_code`。 |
| `identity_account_role` | `account_id BIGINT NOT NULL`、`role_id BIGINT NOT NULL`，两列共同作为主键，各自建立引用账号表和角色表主键的外键。 |

`identity_account.status` 添加 CHECK 约束，仅允许 `ENABLED` 和 `DISABLED`。两个版本列沿用已确认的登录技术评审，初值均为 1。

迁移末尾插入一条 `SUPER_ADMIN` 角色定义。各环境共用这条角色定义，具体账号通过后续步骤建立关联。

## 4. 新增 dev、test 种子迁移

新增 `identity-service/src/main/resources/db/seed/V2__insert_test_accounts.sql`。

1. 准备两个符合中国大陆手机号格式的测试手机号和测试密码，在 SQL 注释中注明测试凭证用途及登录值，供验收使用。
2. 使用 `Argon2PasswordEncoder` 为两个账号分别生成哈希，将生成结果写入 SQL。采用已评审的初始参数，Salt 16 字节、哈希 32 字节、并行度 1、内存 19456 KiB、迭代 2 次。测试中的生成代码可用于一次性生成哈希，随后保留密码匹配断言。
3. 插入两个 `ENABLED` 账号，分别作为普通测试账号和测试超级管理员。
4. 通过手机号查询管理员 ID、通过 `SUPER_ADMIN` 查询角色 ID，插入一条账号角色关联。

使用普通 INSERT，由 Flyway 记录版本控制执行次数。种子 SQL 与正式迁移共享版本编号，V2 已占用，后续正式迁移从 V3 继续。生产库的迁移序列直接从 V1 接续未来的 V3。

## 5. 配置 Profile 和数据源

修改 `identity-service/src/main/resources/application.yml`，在已有 `spring` 配置下补充默认正式迁移目录，保留现有端口、健康检查、追踪与日志配置。

```yaml
spring:
  flyway:
    locations: classpath:db/migration
```

新增同目录的 `application-dev.yml`、`application-test.yml`、`application-prod.yml`，分别使用以下环境变量设置 `spring.datasource.url`、`username`、`password`。

| Profile | URL | 用户名 | 密码 |
| --- | --- | --- | --- |
| `dev` | `IDENTITY_DEV_DB_URL` | `IDENTITY_DEV_DB_USERNAME` | `IDENTITY_DEV_DB_PASSWORD` |
| `test` | `IDENTITY_TEST_DB_URL` | `IDENTITY_TEST_DB_USERNAME` | `IDENTITY_TEST_DB_PASSWORD` |
| `prod` | `IDENTITY_PROD_DB_URL` | `IDENTITY_PROD_DB_USERNAME` | `IDENTITY_PROD_DB_PASSWORD` |

配置采用 `${环境变量名}` 引用实际值。执行人员提前创建三个独立数据库，分别填写对应 JDBC URL，通过 `SPRING_PROFILES_ACTIVE` 选择一个环境。

`application-dev.yml` 和 `application-test.yml` 均追加以下配置，`application-prod.yml` 使用公共配置中的正式迁移目录。

```yaml
spring:
  flyway:
    locations: classpath:db/migration,classpath:db/seed
```

同一 YAML 文件中的配置合并到一个 `spring` 节点。Flyway 负责初始化表结构和对应环境的数据。

## 6. 新增生产预置 SQL 模板

新增 `identity-service/ops/sql/provision_super_admin.sql`，放在应用资源目录之外。模板使用醒目的待替换标记填写手机号和 Argon2id 哈希。

SQL 按 `START TRANSACTION`、插入 `ENABLED` 账号、按手机号及角色代码查询 ID 并插入关联、`COMMIT` 的顺序编写。账号唯一性依赖数据库约束，重复预置时直接报告错误。

执行人员在正式迁移完成后，将模板复制到仓库之外，填入项目负责人指定的手机号和离线生成的 Argon2id 哈希，再通过受控数据库连接执行。执行失败时回滚事务。模板注释注明这些步骤，真实凭证及填写后的 SQL 保存在仓库之外。

## 7. 完成验证并提交

1. 按第 1 节验证三套 Profile 的迁移范围、账号、角色、密码和唯一约束。
2. 配置独立的 `test` 数据库连接，在 `backend/` 执行 `mvn -B clean verify`，确认原有 MVC 与追踪测试继续通过。
3. 检查修改范围、SQL 中的账号用途及凭证来源，提交当前需求相关文件并推送远程仓库。
