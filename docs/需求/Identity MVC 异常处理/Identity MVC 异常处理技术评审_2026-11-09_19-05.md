
# Identity MVC 异常处理技术评审

## 1. 目标行为

Identity 收到 HTTP 请求后，由 Spring Boot 建立请求追踪。MVC 将参数校验失败、不可读 JSON、方法或媒体类型不支持及未预期异常转换为 OpenAPI 约定的 Problem Details。成功响应与错误响应都关联当前请求的追踪，未知异常只记录一次服务端堆栈。

## 2. 最小模型

- 成功响应由已有的 ApiEnvelope 表示。缺少真实 Trace ID 时立即抛错，暴露追踪配置问题。
- 错误响应由 Spring 的 ProblemDetail 表示。HTTP 状态决定标题和顶层错误码，校验错误额外提供安全的字段级说明。
- MVC 请求追踪由 Actuator 的请求观测与 OpenTelemetry 桥接提供。日志关联使用框架注入的 MDC，错误响应从当前 span 读取 Trace ID。

## 3. 实际场景与取舍

- 客户端以错误方法调用接口时，需要通过 Allow 确认支持的方法。沿用 Spring 已计算的响应头。
- 错误实例 URI 尚无实际来源。Spring MVC 默认填入请求路径，使用 Spring 的响应拦截点在序列化前清除。
- 未预期异常通过 SLF4J 记录原始 Throwable，保留诊断消息、堆栈和原因链。业务代码在构造异常时避免写入敏感值。发现实际依赖泄露敏感数据时，针对具体来源处理。
- 网关转发、认证失败、安全审计和远程导出各有独立入口。Identity 的 MVC 请求和日志可在本地完整验证，因此本次仅接入该入口。

## 4. 原有链路

1. IdentityApplication 启动 Spring Boot，加载 identity-service 的 application.yml。生产源码只有启动入口，Actuator 暴露健康检查。
2. Identity 的 POM 已引入 MVC 与 Actuator。请求由 DispatcherServlet 分派，异常由 Spring MVC 的默认解析器处理。Identity 尚无自定义异常处理器。
3. Common 的 ApiEnvelope.ok 与 ApiFailure.of 目前没有后端调用方。它们从 MDC 读取 traceId，缺失时生成随机 UUID。Identity 目前也未依赖 Common。
4. OpenAPI 的 ProblemDetail 已定义 JSON 媒体类型、必填字段和可选的字段校验列表。后端 02 已确定状态、标题、错误码和追踪来源。

源码入口见 [IdentityApplication](../../../xihu-backend-complete-scaffold-v0.2/xihu-backend-blueprint/backend/identity-service/src/main/java/com/swordshield/next/identity/IdentityApplication.java)、[Identity POM](../../../xihu-backend-complete-scaffold-v0.2/xihu-backend-blueprint/backend/identity-service/pom.xml)、[ApiEnvelope](../../../xihu-backend-complete-scaffold-v0.2/xihu-backend-blueprint/backend/common/src/main/java/com/swordshield/next/common/ApiEnvelope.java)和 [OpenAPI](../../../xihu-jian-frontend/openapi/openapi.yaml)。

## 5. 差异、成本与收益

| 差异 | 方案 | 收益与成本 |
| --- | --- | --- |
| Common 可以在无追踪时构造成功响应 | 保留 ApiEnvelope 的入口，MDC 缺少 Trace ID 时直接抛出配置错误。删除无调用方的 ApiFailure。 | 成功响应与日志可以关联。Common 保持原有 SLF4J 依赖。 |
| Identity 没有实际请求 span | 加入 Boot 4 的 Micrometer OpenTelemetry 自动配置模块和桥接依赖。 | 使用现有 Actuator 请求观测和 Boot 日志关联。导出器无须安装。 |
| MVC 默认响应没有项目扩展字段 | 在 Identity 增加一个 RestControllerAdvice，复用 ResponseEntityExceptionHandler 的分派。 | 统一约定内的响应，保留框架提供的头和实际 HTTP 状态。 |
| 无自动化 HTTP 验证 | 用嵌入式服务器和测试专用 Controller 发起真实 HTTP 请求。 | 验证请求观测、实际 JSON、404 和日志关联，测试无需外部服务。 |

## 6. 实现方案

1. Common 移除旧错误响应类型，并使成功响应在缺少追踪上下文时明确失败。
2. Identity 使用 Boot 4 的 Validation Starter、OpenTelemetry 自动配置模块及 Micrometer 桥接。沿用现有 SLF4J 和 Logback。
3. MVC 统一处理 400、404、405、415 和 500。按异常种类添加安全的字段校验信息，保留框架响应头。处理器通过 Spring 原生拦截点省略路径形式的 instance。未知异常在处理边界记录一次原始异常及完整堆栈，对外返回通用说明。
4. 在测试源码中验证成功响应、输入校验、不可读 JSON、405、415、未知异常和 404。核对 Trace ID、日志和响应的关联后，执行完整 Maven 构建。
