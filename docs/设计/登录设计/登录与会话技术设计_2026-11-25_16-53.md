# 登录与会话模块技术设计

依据[业务设计 v1.5](登录设计_2026-11-25_16-53.md)；接口以 [OpenAPI](../../../xihu-jian-frontend/openapi/openapi.yaml) 为准。历史评审中的 Admin JWT 方案不再生效。

## 1. 交付范围与服务职责

统一账号、独立前后台会话。现有父 POM 为 Spring Boot 4.1.2、Spring Cloud 2025.1.4；Gateway 使用 WebFlux，Identity 使用 Servlet MVC、Spring Security OAuth2 Resource Server、JDBC/MySQL、Redis；Admin 采用纯 Redis Spring Session 与 Gateway ForwardAuth。Portal 现有 JWT 安全链保持 STATELESS，不接受 Admin Cookie，资源服务继续独立验证 Portal JWT。

Admin 的 Spring Session 仅由 Identity 创建、读取、续期、销毁。Gateway 统一同步调用 Identity 内部校验接口（ForwardAuth），不直接读 Redis。业务服务接收经验证的当前身份，执行本领域功能和资源授权。Identity MySQL 是账号、角色权威来源；Activity 是场次授权权威来源。

## 2. 接口与会话

| 操作 | Portal | Admin |
| --- | --- | --- |
| 登录 | POST /api/v1/auth/portal/login | POST /api/v1/auth/admin/login |
| 刷新 | POST /api/v1/auth/portal/refresh | 不存在 |
| 退出 | POST /api/v1/auth/portal/logout | POST /api/v1/auth/admin/logout |
| 当前身份 | GET /api/v1/auth/portal/me | GET /api/v1/auth/admin/me |
| Cookie | portal_refresh_token，Path=/api/v1/auth/portal | admin_session，Path=/api/v1 |
| 登录响应 data | AuthSession | AdminProfile（user、roles） |

登录使用中国大陆 11 位手机号和密码，MySQL 保存 Argon2id 密码哈希。手机号不存在、密码错误或账号禁用时统一返回凭证无效；Admin 验证凭证后检查固定角色。沿用现有密码安全及合理登录失败限制，不新增 MFA；正式上线前评估。

Portal Access Token 采用 RS256 JWT，有效期 600 秒，包含账号、会话、应用受众及身份版本等信息，前端保存在内存。Refresh Token 为不透明随机凭证，空闲期限 7 天，绝对期限 30 天。MySQL 只保存 Refresh Token 哈希和轮换记录。浏览器通过 HttpOnly Cookie 持有凭证。生产环境启用 Secure，默认 SameSite=Lax，省略 Domain。涉及 Cookie 的认证接口校验浏览器来源。GET /api/v1/auth/jwks 发布资源服务可用的验签公钥。Portal 登录及刷新返回 Access Token、有效期和用户摘要，摘要包含账号 ID 与脱敏手机号。

### 2.1 Admin 存储选型

- 选 Spring Session Data Redis 的 Servlet `RedisSessionRepository`，由 Spring Boot 依赖管理选择兼容版本；独立 Redis namespace（如 `xihu:admin:session`），空闲超时固定为 **8 小时（28800 秒）**，不设绝对超时。Redis 是唯一 Admin Session 存储，不写 MySQL 会话表或维护 Redis 状态镜像；现有 identity_session/identity_refresh_token 继续服务 Portal，不修改已执行迁移。
- JDBC Session 也可持久化会话，但已明确使用纯 Redis，且项目已有 Redis，不另建关系库会话表。容器内存 HttpSession 不支持多实例共享和重启恢复。
- 按 Session ID 读取、续期和删除当前 Session，普通仓库已覆盖所需操作。封禁和凭证失效由 `credential_version` 在线校验，角色由主库读取。只有将来需要按账号列出或物理清理全部 Session 时，才重新评估 indexed 仓库。
- Session 保存稳定账号 ID、登录时 `credential_version` 和框架必要属性，不使用 Session 中的角色快照授权。不自定义 Session ID、TTL 键或轮换协议。Spring Security 登录成功使用标准 SessionAuthenticationStrategy 防会话固定；自定义 JSON 登录入口须正确保存 SecurityContext。Portal 安全链保持无状态，与 Admin 独立。
- Redis 不可用或 MySQL 无法读取当前状态时拒绝受保护请求，返回 503 AUTH_STATE_UNAVAILABLE；无效/过期或版本不匹配的 Session 返回 401 UNAUTHENTICATED。Redis 丢失会话后重新登录，不从 MySQL 重建。实施时验证 Redis 拓扑、namespace、到期与退出后的并发写回；不预建高可用或补偿框架。

参考：[Spring Session Redis 配置](https://docs.spring.io/spring-session/reference/configuration/redis.html)、[Spring Session API](https://docs.spring.io/spring-session/reference/api.html)、[Spring Security 会话管理](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)、[Gateway WebFlux](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/starter.html)。实际依赖版本、配置和并发行为须在实施阶段编译及集成测试验证。

### 2.2 Gateway ForwardAuth 链路

1. 浏览器 POST Admin login，经 Gateway 转发 Identity；Identity 验证密码、账号启用和至少一个固定角色，创建或更换 Session ID，成功持久化 Redis 后 Set-Cookie 并返回 AdminProfile（Cache-Control: no-store）。
2. 浏览器访问 /api/v1/admin/** 时自动携带 admin_session。Gateway 在转发前删除外部身份头（包括 X-Admin-Account-Id、X-Admin-Roles 及同名重复头），不接受 Portal Bearer 作为 Admin 认证。
3. Gateway 的 Admin 路由过滤器使用响应式 WebClient 同步等待 Identity 内部 /internal/admin/session/validate；仅转发当前 Admin Cookie、必要 CSRF 证明、原请求方法及追踪信息。内部接口不得经公共 Gateway 路由暴露。Identity 从 Redis 读取有效 Session，从 MySQL 主库同一一致读实时检查账号启用、credential_version 和有效角色。返回当前账号 ID 和固定角色，不返回新的凭证；不存在/失效返回 401，无后台资格返回 403 ADMIN_ACCESS_REVOKED，不可用返回 503。Gateway 不缓存结果，不在异常时放行。
4. Gateway 只在校验成功后构造可信身份头，剥离 Admin Cookie 与外部 Authorization，转发给业务服务。业务服务从受信任连接及该头构建本次请求的 Spring Security Authentication，角色映射由所属服务维护；Activity 再从本域数据库查询场次授权、核验状态。不得依据客户端请求中的账号 ID、角色或场次 ID 直接授权。Identity 自有 Admin 业务接口同样经 Gateway ForwardAuth；login、logout、me、csrf 由 Gateway 直接转发 Identity 自身安全链，不重复校验。
5. 信任边界：生产业务服务和内部校验接口不得公开暴露，限制 Gateway 到服务的网络访问。仅删头不足以防直连伪造，部署时验证哪些工作负载能到达两个内部入口：Gateway 到 Identity 校验接口、Gateway 到业务服务。若平台的专用监听或按工作负载隔离的网络策略能证明仅 Gateway 可达，采用该隔离即可。若入口位于共享或跨主机网络，且部署控制无法证明仅 Gateway 可达，使用 mTLS 或现有等价的服务身份认证，并仅允许 Gateway 身份。共享网段或仅按外部头识别来源不足以建立信任。上线前验证其他工作负载无法直连冒用身份；未通过时关闭相应 Admin 路由。
6. ForwardAuth 参考 [Traefik ForwardAuth](https://doc.traefik.io/traefik/middlewares/http/forwardauth/)、[NGINX auth_request](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html)、[OAuth2 Proxy auth_request](https://oauth2-proxy.github.io/oauth2-proxy/configuration/integrations/nginx/)、[Gateway RemoveRequestHeader](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/gatewayfilter-factories/removerequestheader-factory.html)。Spring Cloud Gateway 使用路由过滤器实现这个调用模式，并非声称框架内置 Traefik 中间件。

### 2.3 Cookie 与 CSRF

Admin Cookie 名 admin_session，Path=/api/v1（既覆盖 /auth/admin 又覆盖 /admin），HttpOnly、生产 Secure、默认 SameSite=Lax、host-only（省略 Domain）。生产为 Portal、Admin 分配不同主机名，各自通过同源反向代理暴露所属认证路径。两端 Cookie 均省略 Domain。Gateway 按 Host 分流，在 Portal 路由移除误带的 `admin_session`，在 Admin 路由移除误带的 `portal_refresh_token`，保留同一路由需要的其他 Cookie。本地共享主机时也执行凭证剥离，端口不提供 Cookie 隔离。Portal 安全链不解析、创建或续期 Admin Session，也不签发 `admin_session`。Admin Session 仅设 8 小时空闲期限（28800 秒），不设绝对期限；Cookie 为会话级（省略 `Max-Age`），刷新页面与新开标签页自动恢复，关闭整个浏览器进程后失效，不继承 Portal 的 7/30 天。

浏览器会自动发送 Session Cookie，第三方网页可能诱发发布、核验或退出请求。Admin 登录和业务写请求使用 Spring Security CSRF 防护，仍可使用的 Session 退出同样须校验 CSRF：GET /api/v1/auth/admin/csrf 返回框架 CSRF token（Cache-Control: no-store），前端仅内存保存，写操作通过 X-CSRF-TOKEN 发送。采用 HttpSessionCsrfTokenRepository；登录前可建立无认证的临时 Session，登录后刷新 CSRF token，不把其当作认证凭证。Gateway ForwardAuth 对业务写请求将原方法和 CSRF header 传至 Identity（内部校验使用对应 HTTP 方法以触发标准 CsrfFilter，不转发业务请求体）；拒绝不可信来源，GET/HEAD 不得修改业务状态。校验不通过 403 FORBIDDEN。退出成功后，下次登录或写请求需要时再获取 token，重复退出无需先建立临时 Session。CSRF token 与 Cookie 不是第二认证因素。参考 [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

## 3. 退出与撤权

- **Portal 退出**。先校验来源。用 Cookie 定位当前应用会话，命中尚存会话时撤销该会话以及其 Refresh Token，包括同一会话的已轮换凭证。Cookie 缺失、无法匹配、会话已撤销或已过期时同样返回 `200`。成功均用原名称、Path、host-only 范围清除 Cookie。存储异常导致结果无法确认时返回 `503 AUTH_STATE_UNAVAILABLE`，保留 Cookie 供重试。已签发的 Access Token 保留原定剩余有效期，最多 10 分钟。Portal 账号禁用后不可登录或刷新。
- **Admin 退出**。先校验来源。Cookie 缺失，或 Redis 确认 Session 不存在或已过期时，直接返回 `200` 并清除本端 Cookie，无需 CSRF token。命中认证 Session 时必须校验其 CSRF token，即使账号已无后台角色也可退出。通过后用 Spring Security 使当前 Session 失效，确认后清除同名、同 Path、host-only Cookie 并返回 `200`。匿名临时 Session 不提供账号访问，可随本端 Cookie 清除。Redis 无法确认查询或删除结果时返回 `503 AUTH_STATE_UNAVAILABLE` 并保留 Cookie。其他设备的 Session 独立。
- **账号禁用**。Identity 同事务修改账号状态、递增现有 credential_version、记录审计；禁用提交后的校验一律拒绝。所有旧 Session 由版本检查拒绝，重新启用后仍须重新登录。Redis 条目按正常 TTL 清理。
- **后台角色变更**。Identity 同事务写角色关系及审计。每次 Admin 鉴权实时读取当前有效角色，包括 `me` 和 ForwardAuth。部分撤销后，原 Session 使用剩余角色；无角色返回 `403 ADMIN_ACCESS_REVOKED`。撤权只走这条路径。数据库迁移中的 `permission_version` 和现有 Portal 令牌字段作为兼容字段保留，不用于 Admin 授权。见[账号基础数据建模](账号基础数据建模/账号基础数据建模_2026-11-25_16-17.md)。
- **场次授权撤销**。Activity 同事务撤销领域关联及记录审计；后续核验与记录查询直接依据当前关系，写操作在领域事务内校验。其他场次及角色不受影响。禁止先查全量再过滤。
- 提交后新开始的认证/授权检查不得使用旧状态；已经通过检查且正在执行的请求不承诺跨服务强制中止。若业务要求阻止所有在途写入，须另行确认并设计，不虚构 5 秒 SLA。
- 错误：401 UNAUTHENTICATED（失效或缺少 Session），403 ADMIN_ACCESS_REVOKED（无后台角色），403 FORBIDDEN（业务/CSRF 拒绝），503 AUTH_STATE_UNAVAILABLE（无法确定身份）；不自动刷新，不因普通业务 403 清理身份。

### 3.1 场次授权配置

B27 由 `SUPER_ADMIN` 在账号详情查看、整体替换场次集合，使用 Activity 的 `GET/PUT /api/v1/admin/users/{userId}/check-in-events`。对有效核验员新增关联前，Activity 向 Identity 确认目标账号启用且持有 `CHECKIN_STAFF`，并在本域验证场次存在。查阅及撤销允许处理目标账号的残留授权。场次关系以账号 ID、场次 ID 唯一，关系和实际变更审计同事务提交。角色与场次范围各自由对应服务掌管：残留关系在未持有核验角色时不生效。

核验写入在同一 Activity 事务里按凭证归属核对场次授权。查询在分页前按当前授权过滤。空集合没有核验权限。

## 4. 轮换与多标签页并发

以下轮换规则仅适用于 Portal。

服务端锁定 Refresh Token 所属会话，验证应用、账号启用状态、凭证版本以及会话的撤销状态、空闲期限和绝对期限。通过后再按凭证是否已消费分支。首次消费有效 Refresh Token 时，在同一数据库事务内标记已消费、保存唯一后继的哈希并更新空闲期限，事务成功后才发出带新 Cookie 的响应。宽限期从该令牌首次成功轮换的事务提交时刻起算。

### 4.1 Portal

| 旧凭证状态 | 结果 |
| --- | --- |
| 未消费且有效 | 返回 `200` 与新的 `AuthSession`，通过 `Set-Cookie` 写入唯一后继 Refresh Token。 |
| 已消费，距离首次成功轮换提交不超过 10 秒（含 10 秒） | 返回 `200` 与新的 `AuthSession`，为本次请求签发新的 Access Token，响应中省略 `Set-Cookie`。保留当前会话及轮换结果，空闲期限、绝对期限和宽限期均保持原值。 |
| 已消费，距离首次成功轮换提交超过 10 秒 | 撤销该令牌所属会话及其全部 Refresh Token，记录安全审计，返回 `401 REFRESH_TOKEN_REPLAYED`。 |

各 Portal 标签页正常处理自己的 `200` 响应。单个 HTTP 客户端实例仍合并并发刷新，并在成功后最多重试原请求一次。自动续期返回的 `user.id` 与原请求所属账号不一致时，清理本地旧状态并终止原请求。Portal 刷新由后端判定与浏览器 Cookie 共同处理，前端不实现跨标签页锁、结果广播或等待状态机。发起退出或切换账号的标签页要丢弃本地旧会话的迟到响应，并清理旧私有数据。其他标签页在后续续期失败时清理各自状态。

宽限期内服务端不能从旧凭证判断提交者是否为同一浏览器。若旧凭证已泄露，持有者仍可在窗口内换取有效期为 600 秒的 Access Token。本项目接受这一 Portal 风险，以避免正常并发使用户退出。宽限期没有新的 Refresh Token，也不延长会话续期资格。若首次带 `Set-Cookie` 的响应未送达，后续重复响应只能提供 Access Token，客户端可能在后续续期时需要重新登录。重放处置只撤销所属会话，已签发的 Portal Access Token 按原到期时间失效。[RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)

### 4.2 Admin

浏览器标签页共享 Session Cookie，不需要跨标签页锁、广播、刷新等待状态机、Refresh Token 轮换、重放处理或刷新宽限期。退出/切换账号的标签页清理旧身份和私有数据，忽略旧请求迟到结果。其他标签页下一次请求收到失效响应后清理，不引入实时在线通知。

## 5. 验收条件

- Portal 并发使用同一旧 Refresh Token 时只产生一个后继。恰好 10 秒的重复请求返回 `200` 和有效的新 Access Token，省略 `Set-Cookie`，会话期限和宽限期保持原值。
- Portal 宽限期外使用旧凭证返回 `401 REFRESH_TOKEN_REPLAYED`。失效状态优先于宽限期，账号禁用、版本失效、会话撤销或到期时均不签发凭证。其他设备及另一应用的会话保持有效。
- 两个 Portal 标签页并发恢复或续期时各自消费响应，验证浏览器保留唯一后继 Cookie。发起退出或切换账号的标签页不采纳旧会话的迟到结果。
- Admin 三个固定角色均可登录；普通用户、禁用账号、无 Session 和过期 Session 拒绝。
- 两端针对无 Cookie、无效 Cookie、已退出和过期会话重复退出均返回 `200` 并清除各自 Cookie。不可信来源均拒绝，活动 Admin Session 缺少有效 CSRF 时拒绝。存储不可用且无法确认时返回 `503`，不清除 Cookie。
- 验证生产主机各自只签发并接收本应用 Cookie，共用开发主机时 Gateway 剥离跨应用 Cookie。Portal 请求不创建、续期或写回 Admin Session。
- 伪造身份头、绕过 Gateway、直接访问内部校验端点均不能获得权限；Gateway 每次校验、无缓存，Identity 不可用不放行。
- 禁用提交后所有设备旧 Session 不可用，重新启用不能恢复旧 Session。角色部分撤销后原 Session 仍可使用剩余权限，全部撤销后新请求返回 `403 ADMIN_ACCESS_REVOKED`，Portal 保持有效。
- 首位管理员先在 B27 给核验员配置场次，核验员只在所分配场次核验和查询，随后撤销一个场次。新请求立即失去该场次权限，其他授权场次保持可用。
- 验证并发退出、禁用、续期、角色变化及 Session 删除时不会重新激活无效会话。具体 Spring Session 版本和 Redis 故障行为以实测为准。

## 6. 待确认

实际生产主机名、网络访问规则及是否需要服务身份凭证；是否要求阻止已认证在途写入。不得用待确认项预建通用框架。当前设计不变更 Portal JWT。
