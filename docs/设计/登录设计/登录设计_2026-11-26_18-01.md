# 登录与会话模块业务设计文档

- **项目：** 西湖论剑 · 大会门户
- **模块：** 身份与账号 — 登录与会话
- **版本：** 1.6
- **阶段：** 业务设计
- **状态：** 2026-11-26 确认前后台登录入口、账号导航与页面回跳

---

## 1. 文档目的

本文档定义登录与会话模块的业务范围、业务规则、用户行为及验收边界。

本模块只负责身份认证和登录会话，不负责完整的账号管理、后台角色管理或业务资源授权。

后续接口设计、技术设计和代码实现均必须遵守本文档。

如果技术实现与本文档存在冲突，应先提出问题，不得自行改变业务规则。

## 2. 业务目标

实现大会门户前台和运营后台统一的账号认证能力。

用户使用同一个手机号和密码，可以分别通过前台、后台的独立登录入口建立会话。

系统根据账号状态和后台角色判断用户是否允许登录相应应用。

登录后，用户能够保持登录状态、恢复会话、正常退出。

## 4. 账号与身份规则

### 4.1 统一账号体系

前台普通用户和后台工作人员共用同一套账号体系。

一个自然人对应一个账号，不因其具有后台身份而创建第二套账号。

### 4.2 账号标识

- 手机号是账号的唯一登录标识。

- 全平台一个手机号只能对应一个账号。

- 用户通过手机号和密码登录。

- 仅支持中国大陆 11 位手机号

- 登录时不要求再次进行短信验证。

### 4.3 手机号验证

手机号验证仅属于未来注册业务。

本期不开发短信发送、验证码校验和注册流程。

已有账号的手机号必须已经符合账号创建时的验证要求。

### 4.4 普通用户身份

账号正常启用后，具有普通用户身份。

不需要额外分配普通用户角色才能使用前台。

### 4.5 后台身份

后台身份由账号拥有的有效后台角色决定。

一个账号可以同时拥有多个后台角色。

拥有普通用户身份不意味着自动拥有后台访问资格。

普通用户不能仅凭成功登录就访问后台。

### 4.6 账号状态

本期定义两种账号状态：

| 状态       | 业务含义                  |
| -------- | --------------------- |
| ENABLED  | 账号正常启用，可以进行符合其身份要求的登录 |
| DISABLED | 账号已禁用，不能建立新会话，已有会话失效  |

账号禁用影响整个账号，而不只是某一个应用。

## 5. 前后台登录规则

### 5.1 前台登录

- 使用手机号和密码。

- 账号存在、密码正确且账号启用时允许登录。

- 不要求具有后台角色。

- 登录成功后进入普通用户身份对应的前台。

### 5.2 后台登录

- 使用相同的手机号和密码。

- 后台具有独立登录入口。

- 账号必须存在、密码正确、账号启用，并至少具有一个有效后台角色。

- 没有后台角色的普通用户不能进入后台。

- 登录成功后进入后台，并获取当前账号和后台角色。MVP 准入为 `SUPER_ADMIN`、`EVENT_OPERATOR`、`CHECKIN_STAFF` 中至少一个有效角色。首位管理员仍按现有预置规则建立。

### 5.3 登录失败

以下情况均不得建立新会话：

- 手机号不存在。

- 密码错误。

- 账号已禁用。

- 后台账号没有有效后台角色。

- 其他认证失败情况。

普通登录错误不向外暴露手机号是否注册，避免泄露账号存在性。

后台无角色时应拒绝后台登录，不得自动授予角色。

### 5.4 登录入口与前端交互

**大会门户。** 游客可直接浏览大会首页和公开内容。全站导航右上角提供「登录」，在手机上也保留此入口。登录成功或恢复会话后，同一位置显示「头像图标 + 我的」，展开可进入个人概览和退出。我的报名页面接入后，从个人空间进入报名记录和入场凭证。

| 场景 | 页面去向 |
| --- | --- |
| 在公开页面点「登录」 | 成功后回到原页面。 |
| 游客在场次详情点击「报名」 | 提示登录后可报名。成功后回同一场次，用户继续填写或确认提交。 |
| 直达受保护的站内页面 | 未登录时进入登录页，成功后按权限返回原页面。 |
| 直接打开登录页且没有可用返回目标 | 成功后进入大会首页。 |
| 主动退出 | 在公开页面留在当前页面，在个人空间回大会首页。导航恢复为「登录」。 |
| 会话失效 | 公开页面恢复游客状态，受保护页面跳回登录页并保留原目标。 |

**运营后台。** 工作人员从会务工作指引获取并打开独立后台地址。访问后台根地址或其他业务页面时先确认当前身份，未登录自动进入后台 `/login`。后台登录页提供工作人员手机号与密码表单，两端从各自站点进入。登录后，有权访问原业务页面则返回该页面。没有这类目标时进入本阶段的受保护身份页，后续由工作台 B02 接管默认落点。原目标权限不足时显示无权限提示，并提供返回默认页的入口。没有有效后台角色时，在登录页提示无后台访问权限。已登录时，右上角账号区显示当前角色并提供需确认的退出操作，退出成功后回后台登录页。

**返回目标与失败处理。** 两端用 Vue Router 的 `redirect` 参数保留站内目标及查询参数，登录成功后用 `replace` 完成回跳。页面先验证目标是本站已注册的页面，再由应用的路由守卫检查会话和权限。返回目标不可用时进入本端默认页。服务暂不可用时显示重试，当前登录身份的清理依据服务端确认的会话失效、后台资格撤销或退出成功结果。

## 6. 会话规则

### 6.1 多设备登录

同一账号允许在多个设备同时登录。

不要求新设备登录时强制踢出旧设备。

### 6.2 前后台会话独立

前台和后台分别建立独立会话。

| 操作     | 结果        |
| ------ | --------- |
| 退出前台   | 只退出当前前台会话 |
| 退出后台   | 只退出当前后台会话 |
| 其他设备登录 | 不影响已有设备   |
| 前台退出   | 不影响后台会话   |
| 后台退出   | 不影响前台会话   |

### 6.3 登录状态恢复

用户刷新浏览器或重新打开应用后，在会话仍然有效的情况下，应能够恢复登录状态。

不要求用户每次刷新页面都重新输入密码。

### 6.4 会话刷新

会话有效期管理由系统自动处理。

在符合刷新条件时，系统应允许用户延续登录状态。

Portal 的同一个刷新令牌只轮换一次，首次成功轮换随响应更新浏览器的刷新 Cookie。账号和会话仍有效时，自首次成功轮换提交起 10 秒内（含 10 秒）提交同一旧令牌，系统向各请求返回新的访问令牌，浏览器继续使用首次轮换写入的新 Cookie。重复请求不延长会话期限或宽限期。各标签页独立使用自己的返回结果。

Admin 使用 Redis 托管的服务端 Session，浏览器仅持有会话级 HttpOnly Session Cookie（省略 `Max-Age`，刷新页面或新开标签页可恢复，关闭浏览器进程后失效）。同一浏览器标签页共享 Cookie；仅设 8 小时空闲期限，不设绝对期限，无令牌刷新或跨标签页协调。

Portal 超过宽限期的旧令牌再次使用按重放处理，只撤销该令牌所属的会话。

会话已失效或无法恢复时，用户需要重新登录。

### 6.5 当前会话退出

用户主动退出时，只使当前应用在本设备上的会话失效。两端退出均可重试。当前应用的 Cookie 缺失、无法匹配或对应会话已退出或过期时，确认无可撤销会话后仍返回成功并清除本端 Cookie。浏览器来源校验始终执行。

退出后：

- 当前应用恢复未登录状态。

- Portal 立即撤销当前会话及 Refresh Token，发起退出的标签页清理本地登录状态。同一浏览器的其他标签页在后续续期失败时清理各自的登录状态。已签发的 Access Token 可用到原过期时间，最长再有效 10 分钟。

- Admin 在服务端确认当前 Session 已失效后清除 Cookie 并报告退出成功。仍有效的 Admin Session 必须通过 CSRF 校验才可退出。无法确认退出结果时保留 Cookie 并提示重试。同浏览器其他标签页后续请求被拒绝，其他设备不受影响。

- 不影响其他设备及另一应用的会话。

## 7. 账号禁用与后台权限撤销

### 7.1 账号禁用

账号被禁用后：

- 不允许新建前台会话。

- 不允许新建后台会话。

- 已有会话全部失效。

- Admin 在禁用提交后开始认证的请求不得通过；Portal 按既有 Access Token 剩余期限处理。

账号重新启用后，可以重新登录，不自动恢复已经失效的旧会话。

Portal 最多 10 分钟失效（既有规则不变）；Admin 不设传播宽限期。

### 7.2 后台角色撤销

后台角色撤销只影响后台身份和对应权限。

例如：

某用户原本拥有会务运营角色，角色被撤销后：

- 仍然可以使用普通用户身份登录前台。

- 仍然可以查看自己的个人业务信息。

- 不能继续执行已经撤销角色对应的后台操作。

- 如果不再拥有任何后台角色，则不能继续访问后台。

角色撤销不等同于账号禁用。

后台角色撤销只影响后台访问。角色变更提交后，新开始的后台授权检查按当前有效角色判定。撤销部分角色后，当前会话仍可使用剩余角色。撤销全部角色后，受保护请求返回 `403 ADMIN_ACCESS_REVOKED`。重新授权后，尚未到期且凭证版本仍有效的 Session 按重新授予的角色工作。Portal 会话独立。

### 7.3 权限变化

后台权限发生变更后，不允许旧的登录状态继续提供已经被撤销的权限。

权限变更不要求用户重新注册，也不影响普通用户身份。

### 7.4 固定角色与资源范围

| 角色 | MVP 允许的职责 |
| --- | --- |
| SUPER_ADMIN | 工作人员账号、角色与必要系统配置 |
| EVENT_OPERATOR | 大会活动、议程、报名及基础运营统计（B21） |
| CHECKIN_STAFF | 仅被明确授权的场次的核验及必要记录 |

账号可兼任角色，各角色允许的操作取并集，SUPER_ADMIN 不自动获得其他角色业务操作。核验授权不授予编辑场次或全量报名查看权；授权为空则不能核验。MVP 现场授权范围为报名场次。领取点授权随周边履约纳入后续版本。

### 7.5 核验员场次授权

1. 系统管理员在 B27 给指定账号分配 `CHECKIN_STAFF`，然后在该账号的「核验场次」配置中查看、保存授权场次。按现有公开场次列表选择已发布场次，已保存的关联可单独移除。
2. Activity 按账号和场次保存授权，记录实际增删的操作者、场次和时间。空集合撤销全部场次授权。普通会务运营只负责活动和报名。
3. 核验员在 B05 提交凭证时，Activity 根据凭证关联的真实报名场次检查授权。核验记录查询同样限制在当前授权场次内。撤销提交后，新查询或核验立即使用新范围，其他场次与登录状态保持有效。

角色固定，映射由业务服务维护。不做自定义角色、动态权限组合、继承、显式拒绝、组织树、多租户或字段级授权。审计保留角色分配/撤销、账号禁用/启用、现场核验及重要业务状态变化；记录操作者、目标、结果/变更及时间，由对应业务服务负责，不记录每次浏览。

## 8. 登录安全业务规则

### 8.1 密码认证

- 使用密码进行身份认证。

- 密码错误不得建立会话。

- 不向用户暴露手机号是否存在。

- 密码不得以明文形式保存或记录。

密码具体格式、长度和加密方式在技术设计阶段确定。

### 8.2 登录失败限制

对连续失败的登录尝试实施临时限制，防止暴力尝试。

不采用因连续输错密码而永久锁定账号的规则。

具体失败次数、限制时长和限制维度在技术设计阶段确定。

### 8.3 多因素认证

MVP 不强制要求多因素认证。正式运营涉及真实参会者个人信息前，将 MFA 纳入上线安全评估。

不得为了实现后台登录而额外引入短信登录或其他第二认证因素。

## 9. 首位超级管理员

首位超级管理员通过数据库初始化预置。

初始化数据包括：

1. 管理员账号。

2. 超级管理员角色。

3. 账号与超级管理员角色之间的关联。

管理员账号由项目负责人指定，仅预置 `SUPER_ADMIN`，可先在 B27 分配角色并配置核验场次。项目负责人安排单独的会务运营和核验账号。课设演示由同一人兼任时，通过 B27 显式给首位管理员增加 `EVENT_OPERATOR` 或 `CHECKIN_STAFF`。兼任核验仍须配置具体场次。

密码使用安全的密码哈希保存，不在公开仓库中提交真实凭证。

不开发专门的超级管理员初始化页面或公开初始化接口。

后续其他后台人员通过普通账号体系建立账号，再由具备相应权限的管理员分配后台角色。

## 10. 后续功能边界

以下功能独立于本期登录与会话模块：

### 10.1 注册模块

负责：

- 手机号验证。

- 验证码发送与校验。

- 手机号唯一性检查。

- 密码设置。

- 普通账号创建。

注册产生的账号必须遵循本文档规定的账号体系。

### 10.2 后台权限管理模块

负责：

- 后台账号查询。

- 后台角色查询。

- 角色分配。

- 角色撤销。

- 权限管理。

- 核验员场次授权。

权限管理模块产生的身份与角色变化必须遵守本文档规定的后台准入及权限撤销规则。

### 10.3 密码管理模块

后续负责：

- 修改密码。

- 忘记密码。

- 手机号验证重置密码。

- 密码重置后的会话失效。

密码重置后，所有已有会话失效。

## 11. 业务验收标准

本模块至少通过以下业务场景验收。

| 编号      | 场景         | 预期结果         |
| ------- | ---------- | ------------ |
| AUTH-01 | 正常普通用户前台登录 | 登录成功         |
| AUTH-02 | 正常后台人员后台登录 | 登录成功         |
| AUTH-03 | 普通用户尝试后台登录 | 拒绝登录         |
| AUTH-04 | 错误密码登录     | 拒绝登录         |
| AUTH-05 | 不存在的手机号登录  | 拒绝登录         |
| AUTH-06 | 禁用账号登录     | 拒绝登录         |
| AUTH-07 | 刷新浏览器      | 有效会话恢复       |
| AUTH-08 | Portal 有效会话刷新     | 正常延续会话       |
| AUTH-09 | Portal 失效会话刷新     | 拒绝并要求重新登录    |
| AUTH-10 | 退出当前前台会话 | Refresh Token 立即失效，旧 Access Token 最长再有效 10 分钟 |
| AUTH-11 | 退出当前后台会话 | 退出成功后，旧 Session Cookie 被拒绝 |
| AUTH-12 | 同账号多设备登录   | 多个设备可以同时保持登录 |
| AUTH-13 | 账号禁用 | Admin 后续请求拒绝且撤销全部后台 Session；Portal 按既有规则失效 |
| AUTH-14 | 撤销部分后台角色（后续 RBAC） | 当前会话保留，撤销的权限失效，仍可使用剩余角色 |
| AUTH-15 | 撤销全部后台角色   | 不能继续访问后台     |
| AUTH-16 | 角色撤销后使用前台  | 普通用户身份仍然有效   |
| AUTH-17 | 初始化超级管理员   | 初始账号可登录并管理角色及核验场次，兼任业务角色须显式分配 |
| AUTH-18 | 登录失败信息检查   | 不泄露账号是否存在    |
| AUTH-19 | 同一应用多标签页并发刷新 | 只轮换一次。Portal 宽限期内的重复请求各自取得新的访问令牌，Cookie 只由首次轮换更新。Admin 标签页共享 Session Cookie，不调用刷新接口。 |
| AUTH-20 | Portal 超过宽限期重放旧刷新令牌 | 只撤销该令牌所属会话，其他设备与另一应用保持登录 |
| AUTH-21 | 核验授权撤销或访问未授权场次 | 拒绝核验，其他授权及登录态不受影响 |
| AUTH-22 | 伪造身份头或绕过 Gateway | 不得获得后台访问资格 |
| AUTH-23 | 重复退出、凭证缺失或已过期 | 来源通过后返回成功并清除本端 Cookie。仍有效的 Admin Session 退出须通过 CSRF 校验。 |
| AUTH-24 | 管理员配置、核验员核验、管理员撤销 | 已授权场次可核验并查看记录。撤销后，新核验和记录查询立即失去该场次权限。 |
