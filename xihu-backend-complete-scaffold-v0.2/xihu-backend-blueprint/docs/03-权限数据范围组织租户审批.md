# 03 权限、数据范围、组织、多租户、审批：先做什么，未来如何扩展

## 1. 五种能力是不同的

1. Tenant：资源拥有者/隔离域；不会因 role=ALL 而跨出租户。
2. Org：部门/项目组/会务组织关系；可用于岗位和审批人的解析。
3. Role/Permission：谁可以执行什么操作。权限码稳定，与前端菜单按钮位置解耦。
4. Data Scope：同一个操作允许针对哪些资源实例或关系。
5. Workflow：重要动作需经过什么审批流程，审批的结果不应直接绕过业务服务状态校验。

## 2. 统一授权调用契约

```java
access.require(actor, "checkin:create", ResourceRef.of("event", eventId));
access.require(actor, "user:read", ResourceRef.of("user", userId));
queryScope = access.scopeFor(actor, "registration:read", "registration");
```

- 资源类型与实际范围在 `ScopeDecision` 中显式表示 `ALL/SELF/ASSIGNED/NONE`。`ASSIGNED` 通过业务域的 scoped repository 解释，不返回随意拼装 SQL 字符串。
- UI 的菜单/按钮基于 `permissions` 实现，但具体行操作仍要从后端获取 `allowedActions` 或在点击后接受 403。
- 若用户存在多角色，允许规则取并集，但显式 DENY、租户边界与业务状态先于允许规则；多范围查询必须避免 `OR` 拼错导致越权。
- 对 `SELF` 需要提供字段或业务关系映射，比如 Registration.ownerAccountId，而 User 的 `SELF` 由 User.id 判断。
- 对 `ASSIGNED`：Event 用授权场次集合，User 可用“指定用户集合/由本人负责场次推导的用户集合”，Ticket 可用 assigneeId；统一契约不强行统一 SQL。

## 3. MVP 数据范围配置

- 角色编辑页：设置功能权限 + 范围策略，例如 `checkin:create: ASSIGNED_EVENTS`、`registration:read: ALL`。
- 角色下的共享场次授权：当整组核验员共享场次，可将 `CHECKIN_STAFF` 角色绑定 E01/E02。
- 将来核验组 A/B 分工时，资源集可配置到组织单元；授权算法增加组织角色/组织范围来源。
- 个人特别授权只有明确业务需要才增加，不能把几十个人相同场次逐一配置。
- 菜单和按钮作为 UI 管理能力，可以后续动态化，但安全码不依赖前端路由和菜单 ID。

## 4. 组织架构演进

- 将来新增 `org_unit(id,parent_id,tenant_id,name)`、`org_member(org_id,account_id)`、`org_manager(org_id,account_id)`、`org_role(org_id,role_id)`。
- 身份解析由 `direct roles` 变成 `direct roles ∪ org-inherited roles`，但不能允许组织角色越过租户。
- 组长管理成员：需要 `staff:manage` 权限且 `resource=user` 属于被管理 org；不能仅检查其角色为组长。
- 组织树环路防护、多个组织成员/组长交叉授权、调组后的权限撤销必须测试。

## 5. 工作流演进

- 当前 `publishEvent` 是显式领域状态转换，保证可在接入审批后变为审批完成触发的受保护命令。
- 后续引入 `workflow_definition/instance/task/action_history`，以及审批前的 `draft_revision`；审批对象必须冻结版本，防止审批期间编辑内容。
- 审批人可为具体用户、角色候选组、部门负责人、法务部；任务实际受理时要解析明确候选人并审计。
- 工作流引擎（可选 Flowable）负责流转，不直接更新 Activity/Content 业务表；靠可靠事件或受保护应用服务推进。

## 6. 多租户演进路线与技术成本

| 方案 | 当前实施 | 未来成本 |
|---|---|---|
| 单客户独立部署 | 最少基础设施代码、每客户独立环境 | 批量升级和跨客户账号成本增加，若未来合并数据库重构大 |
| 共享数据库预留 tenantId 但不启用隔离 | 数据模型预备 | **绝不能视为已隔离**；启用前需全面扫 Mapper/文件/缓存/MQ |
| 共享实例真正多租户 | tenant context+成员关系+所有表隔离+测试 | 当前 MVP 工作量和安全审计成本明显增加 |

共享数据库必须做到：JWT 租户身份来自可信认证、租户范围优先于 RBAC、SQL 插入/更新/查询受租户限制、跨租户关联防护、异步消费/定时任务携带租户上下文、缓存键和文件属主隔离、双租户自动化攻击测试。

## 7. 架构验收演化测试（必须通过）

**测试 1：新增用户数据范围，不改 RBAC**
- 配置 `user:read + SELF`，仅允许个人详情。
- 配置 `user:read + ASSIGNED`，增加业务域策略查受托管理的用户；原 `event` 权限逻辑不能被修改。

**测试 2：新增组织组长，不改 EventController**
- 组织角色继承产生 `staff:manage`，用户范围按 org_member 过滤，Event 不受影响。

**测试 3：新增审批，不改通用 REST 安全模型**
- 业务发布命令增加审核结果校验；旧公告/已发布内容的历史版本不能被覆盖。

**测试 4：新增租户 B，所有域一起验证**
- 租户 A 的 Token 不能读 B 的 Event、Registration、CheckIn、File、缓存、统计；即使知道准确 ID、利用批量接口或携带伪造头也不能绕过。
