# 02 工程与编码规范

## 分层与依赖方向

| 职责                    | 约束                                          |
| --------------------- | ------------------------------------------- |
| Controller（接口层）       | 接收请求，做输入格式校验，映射 HTTP DTO 并调用用例。数据库实体留在服务内部。 |
| Application（应用层）      | 编排用例、授权检查、事务与跨边界调用。需要事务的业务写入从用例入口划定边界。      |
| Domain（领域层）           | 维护业务规则、不变量和状态转换。领域规则独立于 HTTP、持久化框架和其他服务的实现。 |
| Infrastructure（基础设施层） | 实现数据库访问、外部客户端及消息等适配。将数据库实体和框架类型留在适配边界。      |

Controller 依赖 Application，Application 调用 Domain。业务需要隔离外部依赖时，在业务侧定义所需契约，由 Infrastructure 实现。包和类随实际职责组织，避免仅为目录对称提前建空包、空接口或一一对应的包装层。公共库仅放与具体领域无关的通用能力，业务实体和策略由所属领域维护。

## API 契约与异常

- 对外接口按仓库 [OpenAPI](../../../xihu-jian-frontend/openapi/openapi.yaml) 约定实现。路径、方法、DTO、ID 表示、时间格式、分页、响应结构、状态码和错误码均查该契约。接口变更先评审并更新 OpenAPI，再修改接口实现。
- 在接口边界校验请求。查询排序使用允许的字段集合。按明确时区转换业务日期，数据库中的时间点按 UTC 保存。
- 普通 JSON 成功响应继续使用 `ApiEnvelope<T>`，包含 `code`、`message`、`data`、`traceId` 和 `timestamp`。成功码为 `SUCCESS`，`message` 仅供辅助展示。
- API 错误响应采用 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)，使用 Spring 原生 `ProblemDetail` 和 `Content-Type: application/problem+json`。响应使用实际的 4xx 或 5xx HTTP 状态，禁止用 HTTP 200 包装失败。

### 错误响应字段

| 字段 | 规则 |
| --- | --- |
| `type` | 固定为 `about:blank`。 |
| `title` | 按[错误分类与状态](#错误分类与状态)取实际 HTTP 状态对应的简体中文标题。 |
| `status` | 必须与实际 HTTP 状态一致。 |
| `detail` | 本次错误的具体说明，必须可安全公开。 |
| `instance` | 可选。仅在有实际错误实例 URI 引用时返回。Spring 默认可能填入请求路径，项目对外响应应省略这类默认值。 |
| `code` | 必填的项目扩展字段，是唯一用于识别业务错误类型的稳定字段。 |
| `traceId` | 必填的项目扩展字段，取自真实请求追踪上下文。 |
| `timestamp` | 必填的项目扩展字段，由服务端生成，采用带时区的 ISO 8601。 |
| `errors` | 可选的项目扩展字段，仅用于字段校验。每项包含 `field`、字段原因 `code` 和安全说明 `detail`。 |

除可选的 `instance` 和 `errors` 外，表中字段均为必填。`title` 和 `detail` 供人阅读。禁止返回泛化的 `details` 对象。错误响应不得包含异常堆栈、类名、SQL、内部服务地址、密码、Token、Cookie 或其他敏感数据。对未知内部异常返回通用说明。

### 错误分类与状态

Gateway、Spring MVC 和 Spring Security 生成错误响应时，都按实际 HTTP 状态取下表的固定简体中文标题。同一状态的标题在各层保持一致，具体失败原因写入 `detail`。新增适用状态时，同步维护本表和 OpenAPI 示例。

| HTTP 状态 | `title` | 适用场景 | 错误码 |
| --- | --- | --- | --- |
| 400 | 请求错误 | 请求格式或参数错误 | `INVALID_ARGUMENT` |
| 401 | 未认证 | 未认证、登录认证失败，或所需认证凭证无效或过期 | `UNAUTHENTICATED`、`ACCESS_TOKEN_EXPIRED`、`REFRESH_TOKEN_EXPIRED` |
| 403 | 禁止访问 | 已认证但无权访问，或认证接口的浏览器请求来源未获授权 | `FORBIDDEN` |
| 404 | 未找到 | 目标资源不存在 | `RESOURCE_NOT_FOUND` |
| 405 | 不支持的请求方法 | 目标资源不支持该请求方法 | `METHOD_NOT_ALLOWED` |
| 409 | 状态冲突 | 业务状态冲突 | `BUSINESS_CONFLICT`、`ALREADY_REGISTERED`、`ALREADY_CHECKED_IN`、`EVENT_FULL` |
| 413 | 请求内容过大 | 请求体超过适用的大小上限 | `PAYLOAD_TOO_LARGE` |
| 415 | 不支持的媒体类型 | 请求体媒体类型不受支持 | `UNSUPPORTED_MEDIA_TYPE` |
| 422 | 无法处理的内容 | 参数格式正确，但不满足业务规则 | `BUSINESS_RULE_VIOLATION`、`REGISTRATION_CLOSED`、`EVENT_NOT_STARTED` |
| 429 | 请求过于频繁 | 请求超过适用的频率限制 | `TOO_MANY_REQUESTS` |
| 500 | 服务器内部错误 | 未预期的内部错误 | `INTERNAL_ERROR` |
| 502 | 网关错误 | Gateway 收到无效的上游响应 | `BAD_GATEWAY` |
| 503 | 服务不可用 | 目标服务暂不可用 | `SERVICE_UNAVAILABLE` |
| 504 | 网关超时 | Gateway 等待上游响应超时 | `GATEWAY_TIMEOUT` |

顶层错误码采用大写下划线命名，在整个项目内保持唯一、稳定。同一码在各服务中表示相同语义。保留已有业务码及其 HTTP 状态，新增错误码时先在 OpenAPI 记录适用场景和 HTTP 状态。接口只声明适用的错误响应，路由级或基础设施级错误按实际生效范围使用公共响应定义。

### 处理职责

- Spring MVC 使用 `@ControllerAdvice` 和 `ResponseEntityExceptionHandler` 统一处理 MVC 异常，并在 HTTP 边界将业务失败映射到错误码和状态。
- Servlet 环境的 Spring Security 使用 `AuthenticationEntryPoint` 处理未认证，使用 `AccessDeniedHandler` 处理权限拒绝。WebFlux 环境使用对应的响应式安全入口与拒绝处理器。
- Spring Cloud Gateway 使用 WebFlux 的全局异常处理机制处理网关自身异常及上游调用失败。下游已经返回符合契约的 Problem Details 时，透传其 HTTP 状态、媒体类型与响应体。
- Common 仅提供跨服务确需共享的错误码和响应通用能力，禁止引入 MVC 或 WebFlux 依赖。Domain 表达业务失败及其原因，保持独立于 HTTP 状态、Spring MVC 和 WebFlux。

各处理边界均遵循同一 Problem Details 契约。

## 数据访问与迁移

- 表和列用 `snake_case`，Java 字段用 `camelCase`。同一模型采用一致的主键策略。业务记录明确保存账号、场次、大会等适用归属，归属字段由业务服务依据可信数据写入。
- 各服务维护自己的版本化数据库迁移，已执行的迁移只通过新增版本演进。生产环境禁止自动改表及加载演示数据。
- 业务唯一性与幂等约束应落实到数据库。写入一致性见 [事务与一致性](01-总体架构与数据所有权.md#事务与一致性)，受保护数据的读写见 [数据库中的范围约束](03-权限数据范围组织租户审批.md#数据库中的范围约束)。
- 密码、会话令牌及凭证按用途保存必要的安全表示或元数据。禁止把明文密码、完整 JWT 或完整核验令牌写入业务表。

## 配置、部署与可观测性

- 环境相关配置外置，真实密钥与密码从环境或密钥系统取得。演示凭证和开发默认值仅用于本地。固定构建依赖版本，升级须验证整套依赖的兼容性。
- 区分存活与就绪检查。为实际依赖的下游设置超时并按需限制请求量。新增中间件应服务于已明确的业务或运行需求。

## 日志与审计

### 记录分类与职责

| 记录 | 职责 | 去向 |
| --- | --- | --- |
| 应用运行日志 | 诊断服务启停、数据库和外部依赖故障、后台任务执行、未预期异常及重要运行或业务事件。 | 标准输出 |
| HTTP 访问日志 | 由 Gateway 在外部请求结束时记录一条访问摘要，覆盖网关直接处理和转发下游的请求。下游业务服务记录自身关键业务事件和异常，避免重复记录常规请求的访问摘要。成功的例行健康检查不逐次写入 INFO，异常仍按实际情况记录。 | 标准输出 |
| 安全审计记录 | 追溯重要业务操作与安全事件，由事件所属业务服务追加写入。 | 所属业务服务的数据库 |

### 日志框架、格式与部署

- 运行日志和 HTTP 访问日志沿用 SLF4J、Logback 和 Spring Boot 原生日志配置。本地开发使用可读文本，通过 IDEA 或终端查看。测试和生产环境使用 Spring Boot 原生 ECS JSON，每行一个 JSON 事件。优先使用原生字段映射与扩展配置，避免自建序列化器或引入额外日志依赖。见 [Spring Boot 日志文档](https://docs.spring.io/spring-boot/reference/features/logging.html)。
- 部署环境从标准输出采集并存储日志。Docker 部署使用容器日志机制，日志轮转和保留由部署环境负责，保留期限根据日志类型和部署要求确定。业务服务不自建运行日志上传、日志数据库或日志管理平台。本阶段不引入 ELK、Loki、Graylog 等集中式日志平台。

### 结构化日志字段

采用 ECS 作为基础字段规范，允许使用本表明确登记的 OpenTelemetry Semantic Conventions 字段作为扩展。新增项目自定义字段统一使用 `swordshield.*` 命名空间，避免占用 ECS 或已登记的扩展字段。见 [ECS 字段规范](https://www.elastic.co/docs/reference/ecs/ecs-field-reference)。

| 字段 | 来源 | 含义与使用规则 |
| --- | --- | --- |
| `@timestamp`、`log.level`、`message` | ECS | 事件时间、日志等级、安全且便于阅读的事件描述。 |
| `service.name`、`service.version` | ECS | 产生日志的服务名、运行版本。 |
| `trace.id`、`span.id` | ECS | 当前追踪和当前 span 的标识，从真实追踪上下文取得。 |
| `user.id` | ECS | 已验证的操作人 ID，适用时记录。 |
| `http.request.method`、`http.response.status_code` | ECS | 请求方法和实际返回的 HTTP 状态码。 |
| `http.route` | OpenTelemetry Semantic Conventions | 已匹配的路由模板，如 `/events/{eventId}`。无法可靠取得模板时省略，禁止猜测或填入实际请求路径。 |
| `url.path` | ECS | 实际请求路径。Gateway 常规访问摘要不采集此字段。 |
| `event.category` | ECS | 事件分类，使用 ECS 允许值的数组，例如 `["authentication"]`。 |
| `event.action` | ECS | 稳定的操作名称。 |
| `event.outcome` | ECS | 从事件记录方视角填写 `success`、`failure` 或 `unknown`。 |
| `event.reason` | ECS | 必要且经过安全处理的原因。 |
| `event.duration` | ECS | 操作耗时，使用整数纳秒。 |
| `source.ip` | ECS | 必要时记录可验证来源的 IP。 |
| `user_agent.original` | ECS | 仅在必要的安全事件中记录，按日志安全要求处理。 |

每条运行日志与访问日志记录时间、等级、描述、服务名和版本。有追踪上下文时自动附上追踪字段，其余字段按事件类型选择。Gateway 访问摘要记录请求方法、匹配的路由模板（可可靠取得时）、实际 HTTP 状态码（已返回时）、耗时和 Trace ID。

访问摘要不采集请求体、响应体、URL 查询参数、Cookie 或 Authorization 请求头。仅在有诊断或安全需要且来源可信时记录 IP。经过代理时，按部署明确的可信代理范围解析转发地址，不能直接采用外部请求传入的 `X-Forwarded-For`。

字段定义见 [ECS Event 字段](https://www.elastic.co/docs/reference/ecs/ecs-event)和 [OpenTelemetry HTTP 语义约定](https://opentelemetry.io/docs/specs/semconv/http/http-spans/)。

### 日志等级与事件命名

| 等级 | 用途 |
| --- | --- |
| TRACE | 非常详细的内部执行信息。 |
| DEBUG | 开发调试信息。 |
| INFO | 正常运行及重要业务事件。 |
| WARN | 已处理且需要关注的异常情况。 |
| ERROR | 未预期的系统故障。 |

本地开发可对项目自身包启用 DEBUG，第三方依赖保持 INFO 或 WARN。测试和生产环境的根日志级别默认 INFO。生产环境临时启用 DEBUG 或 TRACE 时，限定包或组件和启用时段，到期恢复。

操作采用稳定的领域和操作命名，例如 `auth.login`、`auth.logout`、`identity.role.assign`、`identity.account.disable`、`activity.event.publish`、`activity.checkin`、`report.export`。审计记录的操作名称沿用同一规则。同一操作通过 `event.outcome` 或审计结果字段区分不同结果。密码错误按安全事件处理，重复报名按业务冲突处理，这两类预期失败均不打印 ERROR 堆栈。未预期的数据库连接故障按系统异常处理。

### 分布式追踪

- 使用 Spring Boot Actuator 的 Micrometer Tracing 支持，通过 W3C Trace Context 在 Gateway 与下游服务之间传播上下文。HTTP 入口须在路由、认证或异常处理可能生成响应前建立追踪上下文。收到有效且来自可信上游的上下文时接续该追踪，否则建立新的追踪。Trace ID 仅用于关联，不能作为身份或授权依据。见 [Spring Boot 追踪文档](https://docs.spring.io/spring-boot/reference/actuator/tracing.html)和 [W3C Trace Context](https://www.w3.org/TR/trace-context/)。
- 日志自动关联当前 Trace ID 和 Span ID。使用 MDC 时，将框架提供的 `traceId` 和 `spanId` 映射为 ECS 的 `trace.id` 和 `span.id`，同一条 JSON 日志只保留一套追踪字段。在 WebFlux 和其他异步执行边界随请求传播上下文，请求结束后退出作用域并清理 MDC 或相应上下文，避免污染后续请求。
- `ApiEnvelope` 和 [Problem Details](#错误响应字段) 的 `traceId` 均取自真实请求追踪上下文，与该请求日志中的 `trace.id` 一致。禁止在构造响应时生成随机 UUID 充当 Trace ID。
- 当前 `ApiEnvelope.ok(data, traceId)` 由调用方提供真实请求 Trace ID，传入空值或空白字符串时抛出 `IllegalArgumentException`。HTTP 接口层负责从当前追踪上下文取得 Trace ID。旧 `ApiFailure` 已移除，错误响应采用 Spring 原生 `ProblemDetail`。Gateway 和 Identity 已接入 Micrometer Tracing，其他服务随实际接口开发接入并验证。
- ECS 约定日志字段，Micrometer Tracing 与 W3C Trace Context 负责建立和传播追踪上下文。可按需通过 OpenTelemetry 导出追踪数据。本阶段不要求部署 Jaeger、Tempo、OpenTelemetry Collector 或其他追踪平台。

### 安全审计持久化

- **归属**。遵循[领域与数据所有权](01-总体架构与数据所有权.md#领域与数据所有权)。Identity 持久化自己的身份与安全审计记录，Activity 持久化自己的活动业务审计记录，其他业务服务按事件归属持久化。各服务使用自己的数据库和本地事务。禁止跨服务写审计表、共享写入审计表、独立部署 Audit 微服务或在 Common 中引入审计数据库访问逻辑。普通运行日志仅供诊断，不能代替持久化审计记录。
- **范围**。身份及授权事件见[安全审计事件](03-权限数据范围组织租户审批.md#安全审计事件)。Activity 至少审计大会发布及重要状态变更、重要报名管理操作、现场核验成功、重复核验等异常操作，以及管理员的重要活动操作。其他领域按需补充高价值操作，例如敏感报表导出。普通公开页面浏览和常规列表查询无需逐次持久化。
- **逻辑字段**。记录事件唯一标识、发生时间、操作人类型及 ID、操作名称、资源类型及 ID、操作结果、必要的失败原因、Trace ID、必要的可信来源 IP 和变更摘要。发生时间按 UTC 保存。匿名请求或登录失败时，操作人 ID 可为空。事件没有关联请求或目标资源时，相应标识按实际可得信息记录。变更摘要仅保留必要且允许记录的字段及其前后值或状态。
- **事务**。需审计的关键状态变更与对应审计记录在所属服务的同一个本地数据库事务内写入。审计写入失败必须回滚关键状态变更。登录失败、权限拒绝等没有关联状态变更的安全事件独立持久化，业务事务回滚不能撤销该安全记录。审计存储故障须记录脱敏诊断信息并纳入监控。独立事件的写入故障是否影响认证或相关操作，按事件风险另行确定。
- **保护与查询**。应用层只允许追加，普通业务接口不得修改或删除历史记录。审计查询须有独立权限。追加约束适用于应用层，数据库管理员仍拥有数据库层的管理权限。本阶段只规定逻辑字段和行为，SQL 表结构、管理员查询功能和防篡改存储均在本阶段范围之外。后续如需跨服务查询，可通过数据交换或事件汇总构建统一读模型，写入责任仍归源服务。

### 日志与审计安全

- 禁止记录密码、Access Token、Refresh Token、Cookie、Authorization 请求头、数据库连接密码、加密密钥、二维码凭证原文、完整敏感请求体及 SQL 参数中的敏感值。审计记录禁止保存完整个人信息、请求体或数据库实体。手机号、邮箱等个人信息默认省略，确需记录时脱敏。
- 使用参数化日志和结构化字段，禁止直接拼接外部输入。对可记录的外部字段限制长度，按输出格式编码或转义换行符和其他控制字符。JSON 使用原生编码，文本日志也要防止用户输入伪造新日志行。参数化调用本身不负责转义。
- 业务代码在构造异常时不得把密码、Access Token、Refresh Token、Cookie 或完整敏感请求体等敏感数据拼入消息。预期业务失败优先使用稳定错误码和安全说明，保留正常的异常原因。发现实际依赖的异常消息包含敏感数据时，针对该来源处理。

### 异常日志

- 普通参数校验、业务冲突等预期失败只按需记录必要上下文，省略完整 ERROR 堆栈。认证或权限异常记录必要的安全事件，适用时按[安全审计持久化](#安全审计持久化)处理。
- 未预期的 500 异常由负责处理的服务端边界通过 SLF4J 记录一次原始异常及完整堆栈，保留消息和原因链。异常处理器无需默认删除消息、修改或复制 Throwable、对全部异常消息运行通用正则脱敏或引入统一脱敏框架。同一服务的调用链各层不重复打印同一个异常的堆栈。下游调用失败时记录安全的目标服务标识、耗时和异常类型，按故障情况补充实际状态码。Gateway 透传下游 Problem Details 时只记录访问摘要，不对已由下游处理的异常重复打印堆栈。
- 未预期异常的 Problem Details 遵循 [API 契约与异常](#api-契约与异常)，对客户端仅返回安全的通用说明。内部异常消息、堆栈和诊断信息留在服务端。

## 测试与发布

| 层次      | 验证内容                                                            |
| ------- | --------------------------------------------------------------- |
| 单元测试    | 覆盖适用的业务规则、状态转换、授权策略及拒绝行为。                                       |
| 数据库集成测试 | 使用实际选用的数据库验证迁移、事务回滚、约束及复杂授权查询。对并发报名、重复核验等存在竞争的操作验证原子性与幂等。       |
| 安全测试    | 验证未认证、无操作权限、错误资源范围和适用的租户隔离。覆盖相关的详情、列表、统计、导出和批处理，断言响应及数据库结果符合预期。 |
| 契约测试    | 对照 OpenAPI 校验代表性的成功和错误响应。发布前运行适用的单元、集成、安全和契约检查。                 |

日志与审计落地后，至少验证以下行为。

1. 测试与生产配置输出逐行可解析的 ECS JSON，关键字段及类型符合约定，`event.duration` 使用纳秒。
2. Gateway 和下游服务共享同一 Trace ID，各自使用当前 span 的标识。成功响应、路由或认证拒绝、业务异常及未知 500 的响应 `traceId` 均可关联日志。覆盖缺失、无效或不可信的外部追踪头，以及异步处理和请求结束后的上下文清理。
3. 预期校验和业务失败无完整堆栈，未预期异常在负责边界只有一份完整堆栈，错误响应不包含内部诊断详情。
4. 密码、Token、Cookie 等敏感值不会出现在日志或审计记录中。包含换行符的外部输入在文本和 JSON 输出中均无法伪造新事件。
5. 关键业务写入与审计记录一同提交。模拟审计写入失败，确认关键状态未提交。独立的登录失败或权限拒绝记录可单独持久化。
6. 普通业务接口无法修改或删除历史审计记录。未来提供审计查询时，验证其独立权限。
7. 外部请求只由 Gateway 输出常规访问摘要，下游服务不重复记录。匹配路由时记录模板，无可靠模板时省略，例行健康检查不刷 INFO，伪造转发头无法成为可信来源 IP。

历史技术基线与当前工程的差异见 [待确认事项](11-现有前端OpenAPI契约差异与冻结项.md)。
