# 09 多资源数据范围的运行设计

## 1. 对 MVP 与未来共同成立的不变量

```
有效访问 = 可信身份 + 当前租户成员关系 + 功能权限 + 资源范围 + 业务状态
```

租户边界先于角色范围；`ALL` 是当前租户范围内全部，绝不是跨租户全部。未得到规则/缺失上下文时拒绝。平台超级管理员权限需要独立的高信任能力，不能在业务服务中以 `SUPER_ADMIN` 字符串静默绕过隔离。

## 2. 数据与配置分层

- `permission_catalog(code, resource_type, action)`：稳定动作名，例如 `user:read`, `checkin:create`，通常平台级字典。
- `role`、`role_permission_scope(role_id, permission_code, scope_kind)`：角色共同功能与范围策略，不把权限仅存菜单表。
- `role_scope_target(role_id, permission_code, resource_type, resource_id)`：当前按角色共享 E01/E02 等授权资源；需要保证同租户内资源有效。
- 未来 `org_scope_target(org_id, permission_code, resource_type, resource_id)`：组织/组的授权来源。
- 未来 `user_scope_exception(...)`：少量确实需要的个人例外，须明确撤销和与角色授权如何合并。
- `user_role`、`org_member`、`org_role`：不同授权主体来源，不等于业务数据拥有权。

**默认多个角色的允许范围取并集；无授权一律拒绝。** 不设计通用 `DENY` 策略表达式与任意 SQL 规则编辑器；未来如确有拒绝覆盖需求，需重新明确定义优先级。范围种类 `ALL`/`SELF`/`ASSIGNED` 是策略代码，具体关联关系由业务领域解析。

## 3. 重点区分 SELF 的含义

不能仅以 `resourceId == currentUserId` 判断 `SELF`。例如报名记录 R9 的 `resourceId=R9`，但 `ownerId=U1`；`registration:read SELF` 应匹配 **报名归属用户 U1**，而不是匹配 R9。Activity 的报名视图需从服务端已落库的 `account_id` 取 ownerId，禁止相信客户端输入。

`AuthorizationRequest` 明确带 `actorId, tenantId, permissionCode, resourceType, resourceId, ownerId`。`AuthorizationGrant` 把授权来源解析为具体种类与资源集合，`AuthorizationGrantEvaluator` 仅负责纯规则比对。`ownerId` 和资源的租户归属必须来自可信业务数据查询，不得来自前端。

## 4. 各资源范围由自己的领域实现

| 操作 | 资源类型 | 可行范围 | 查询方 |
|---|---|---|---|
| `checkin:create` | event | 全部 / 指定场次 | Activity |
| `event:update` | event | 全部 / 指定场次 / 未来指定组织 | Activity |
| `user:read` | user | 全部 / 指定用户 / 关联业务用户 | Identity + 业务授权查询 |
| `registration:read` | registration | 本人 / 授权场次下的报名 | Activity |
| `article:update` | article | 全部 / 本人创建 / 指定内容 | Content |
| `exhibitor:update` | exhibitor | 全部 / 指定展商 / 组织负责 | Content |
| `ticket:handle` | ticket | 本人负责 / 本工作组 / 全部 | Customer Service |

## 5. 列表/统计/导出不能在内存中事后过滤

- 详情访问：先按当前租户查到实体，再校验角色权限和资源归属。
- 列表访问：把 `AuthorizedQuerySpec` 编译成 WHERE / EXISTS 子句，**在 LIMIT、COUNT 之前过滤**；不能查全表再过滤。
- 统计/导出：使用同一条数据授权约束，防止报表泄露。
- 使用 MyBatis / MyBatis-Plus 时，自定义 XML/JOIN、批量 UPDATE、逻辑删除、原生 JDBC 均需专门审查。
- 任何 `ASSIGNED` 空集合应解释为无数据，严禁转换成不带 WHERE 的全量查询。

## 6. 前端表现

菜单和按钮关联业务权限码；角色页可以设置操作权限及数据范围策略，指定资源多选控件取决于资源类型。具体资源关系可在角色页统一配置，也可在场次/组织页面反向配置，但最终写入同一授权关系。前端隐藏不是安全边界。

## 7. 现有实现状态

原有 `ScopeDecision` 用 `actorId == resourceId` 处理 SELF：仅对用户资源这类特例成立；已增加 `AuthorizationRequest` + `AuthorizationGrant`，修正通用 SELF 比对为可信 ownerId。但现有 Activity 演示代码暂未切换为数据库授权策略解析，仍需在 MVP 验收时完成替换。
