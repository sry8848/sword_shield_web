# 10 多租户、组织、审批的增量演进与重构明细

## 1. 多租户：三种独立部署选择

- 当前应用仍为单租户示范，`tenant_id=default` 仅为数据归属演示，不是已实现安全多租户。
- **共代码独立部署**：每客户独立实例/数据库，无共享查询隔离问题；增加部署模板、密钥与 Flyway 管理，不必强制 `TenantLineInnerInterceptor`。
- **共享应用 + 共享表**：新增可靠租户解析、成员身份校验、租户上下文、SQL 自动租户过滤、租户复合唯一约束与外键、Redis/file/MQ/定时任务上下文及隔离测试。
- **共享应用 + 独立数据库**：改为租户数据源路由，增数据库创建/连接池/迁移/故障处置机制。

不在三个模式之间做静默切换。若以后真实采用共享 SaaS，不能仅凭 `tenant_id` 就宣称隔离。

## 2. 组织树升级

旧：`account_role` 直接授予角色。新增加：

```
org_unit(id, parent_id, tenant_id, type)
org_member(org_id, account_id)
org_manager(org_id, account_id)
org_role(org_id, role_id)
org_scope_target(org_id, permission_code, resource_type, resource_id)
```

保留原用户角色关系，授权解析新增 `OrgMembershipResolver`；业务服务仍以统一授权请求检查，不直接 JOIN 组织层所有表。组织负责人审批人与组长管理员的范围由组织服务查询。

如果当前实现硬编码 `CHECKIN_STAFF` 或到处手写 SQL，则这些调用必须逐一迁移；若按 `AuthorizationRequest` + 领域 `AuthorizedQuerySpec` 规范实现，变化主要集中授权解析器、资源查询编译器。**仍需测试所有列表、详情、统计、导出与批处理**。

## 3. 审批升级

第一版：`event.publish(id)` 独立业务命令，在领域内校验状态+权限+审计。未来：

```
SubmitForReview -> ApprovalInstance(reviewed_revision_id)
  -> ApprovalTask(assignee_or_candidate_group)
  -> ApprovalDecidedEvent
  -> BusinessPublishCommand(revision_id, approval_id)
```

新增业务修订版本、审批实例/任务/日志、回调幂等及归属组织解析。审批引擎不允许跨库直接更新事件/资讯状态。

对于已发布内容的编辑，需要独立草稿/发布版本；这会涉及内容表和读模型重构。现在未实现的不能被描述为“完全零重构”。

## 4. 明确何处可能发生大重构

| 将来需求 | 现在无预留的后果 | 按当前分层设计后的主要变化 |
|---|---|---|
| 新角色和菜单 | Controller 中大量按角色判断 | RolePermission 数据、前端菜单配置；业务权限码不动 |
| 指定用户/展商/场次授权 | 各处自己拼 WHERE | 该领域新增关系表/授权查询编译策略 |
| 核验组长管理成员 | 用户角色全局化导致角色爆炸 | OrgMember/OrgRole/OrgManager + 管理权限范围 |
| 部门负责人审批 | 审批人写死在文章表 | 组织管理者解析和 Workflow Task |
| 内容版本审批 | 已发布内容被原地覆盖 | 新建 revision 表、发布引用、内容审核状态 |
| SaaS 共享表 | 所有资源没归属，缓存没有 namespace | DB 迁移、用户归属、SQL/缓存/文件/MQ 漏洞审计；仍是跨域大改 |
| 独立部署多个客户 | 配置写死 | 环境变量 + Compose/K8s 部署模板，无需强制 tenant_id |

这不是工期承诺。一次性导入所有未来表并不能省掉真实业务变化的研发和测试。
