# 06 权限数据模型、接口与扩展契约

## 1. 用户、角色、权限及组织关系

MVP 逻辑关系（仅业务设计，**示范骨架中的 identity 仍使用内存账号**）：

```text
account                       id, phone/login_name, password_hash, status
role                          id, code, name, status
permission                    id, code, resource_type, action, description
account_role                  account_id, role_id
role_permission               role_id, permission_id, scope_policy

role_resource_grant            role_id, permission_id, resource_type, resource_id
```

`role_resource_grant` 代表角色共享的一组“具体资源”，而不是通用资源表。对于简单 Event 可以保存资源 ID；对于报名用户的复杂关联范围，仍应由业务查询规则实现。字段包含 `resource_type` 和 `permission_id`，避免角色获得 E01 的核验权后顺带拥有 E01 的编辑权。真实实现时应使用角色/资源/操作联合唯一约束和来源校验。

未来组织：

```text
org_unit                      id, tenant_id, parent_id, type, name, status
org_member                    org_unit_id, account_id
org_manager                   org_unit_id, account_id
org_role                      org_unit_id, role_id
org_resource_grant            org_unit_id, permission_id, resource_type, resource_id
```

**组织不等于租户**。未来同一个用户可在不同组织任职，在跨租户业务里必须再施加 `tenant_id` 限制。角色继承必须有作用域、撤权和冲突规则。

未来租户：

```text
tenant                        id, slug, name, status
tenant_member                 tenant_id, account_id, status
tenant_member_role            tenant_id, account_id, role_id
```

共享式多租户需要在租户业务表中保存归属字段并加索引。`ALL` 只意味着当前租户内全部资源；不能访问其他租户的任何数据。全局 `account` 是一种建议，不是所有 SaaS 的唯一选择。

## 2. 三层授权原则

**功能权限**：`hasAuthority('event:update')` 判断账号是否能执行操作。

**资源范围**：`access.require(actor, 'event:update', ResourceRef('event', id))` 判断是否能对该事件执行操作。

**业务条件**：`event.status == DRAFT`、事件开始时间未超过锁定点、容量满足规则等；不是数据权限。

必须按顺序拦截，**fail-closed**；缺少映射、未知策略、授权服务不可用时不放行。查询必须在数据库层应用范围（包括 `count(*)`, `export`, `update where ...`），不能先分页查全表后在 Java 中过滤，那会泄漏总数并造成页不满。

## 3. 统一接口（目标形态）

```java
interface AuthorizationService {
    void requireFunction(Actor actor, String permissionCode);
    void requireObject(Actor actor, String permissionCode, ResourceRef resource);
    QueryScope resolveQueryScope(Actor actor, String permissionCode, String resourceType);
}

sealed interface QueryScope permits AllScope, SelfScope, AssignedScope, NoneScope {}
```

数据库适配器根据 QueryScope 构造白名单列、参数化的查询谓词：

| ResourceType | SELF 如何计算 | ASSIGNED 如何计算 |
|---|---|---|
| event | 可能没有 SELF | 已分配事件 ID、负责部门事件 |
| user | `account.id = actor.id` | 明确分配用户，或被授权事件的参会人（经报名关系） |
| registration | `registration.account_id = actor.id` | 已授权事件下的报名记录 |
| article | `created_by = actor.id` | 编辑职责或内容团队分配 |
| ticket | `requester_id = actor.id` | `assignee_id = actor.id`、团队工单 |

**多资源类型意味着接口统一，查询具体语义仍由业务域负责**；切忌使用任意 SQL 条件字符串作为通用授权结果。

## 4. 管理配置界面（目标，不等于 MVP 全部实现）

角色管理：选角色 → 勾选 `event:read`, `checkin:create`, `user:read` 等权限 → 为每个权限选择数据范围策略（ALL/SELF/ASSIGNED/业务关系）→ 若为 ASSIGNED，提供绑定资源/部门列表的入口；相同职责的人可以共享角色资源范围，无需每人重复配置。

人员管理：给账号分配角色。未来组织管理：账号可加入组织、组织可以被授予角色和资源范围。角色、组织、个人多种授权来源合并时必须遵循明确优先级，不得由“先取到哪个角色”决定结果。

菜单与按钮：菜单关联稳定权限码；前端只能决定显示和提示，不承诺后端数据权限。动态菜单及按钮资源管理属于后续 UI 能力，MVP 可以用静态路由。

## 5. 启用真实权限时不可省略的工作

- 把本包 identity 的内存账号和写在 JWT 的权限列表迁移到真实角色数据库。
- 设计权限变更后立即或有界生效；不能让老 JWT 在角色撤销后持续越权。
- 角色授权范围必须可审计，并有操作人、操作时间和撤销记录。
- 所有后台资源列表/详情/导出/批量处理统一走授权服务的受控 QueryScope。
- 增加活动授权的集成测试，再增加用户、内容等第二资源类型的反向验证。
