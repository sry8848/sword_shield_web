# 01 总体架构与数据所有权

## 领域与数据所有权

下表约束逻辑职责及主数据归属。业务实施顺序和交付范围见 [规范入口](../README.md)。

| 领域               | 拥有的数据与规则                                                                     |
| ---------------- | ---------------------------------------------------------------------------- |
| Gateway          | 对外路由、请求追踪与入口治理。业务用例、业务表和授权关系由所属服务维护。                                         |
| Identity         | 账号、会话、角色、权限及账号直接角色分配。                                                        |
| Activity         | 大会届次、会场、嘉宾、场次、普通报名、参会凭证、现场核验及其基础统计口径。                                        |
| Content          | 资讯、投稿、展商、成果、资料和媒体元数据。维护内容草稿与公开版本的边界。                                         |
| File             | 文件对象、存储元数据、上传、下载和清理。业务关联与可见性归所属业务域。                                          |
| Interaction      | 评论、点赞、签名墙、提问、反馈和参会交流等互动关系。目标资源的存在性与公开性归目标域。                                  |
| Incentive        | 日常签到、任务、积分流水和奖品。积分变更按唯一业务流水做幂等，场次到场记录归 Activity。                             |
| Limited Seat     | 限量批次、库存配额、占席、候补、释放及对应核销。占用和释放有明确归属，限量预约使用独立于普通报名的状态规则。                       |
| Payment          | 支付单、退款单、回调与对账。付款状态由支付域根据验签后的回执确认，重复回调须幂等。                                    |
| Customer Service | 客服知识、会话、人工工单、工单分配与答复反馈。报名、席位和支付状态向对应业务域读取。                                   |
| Analytics        | 跨域汇总、渠道转化及分析读模型。各业务域维护源事实和原始统计口径。                                            |
| Workflow         | 审批实例、任务、办理记录和结果。业务状态归业务域。                                                    |
| Organization     | 组织树、成员、负责人及组织角色关系。与 Identity 的未来部署及存储归属见 [待确认事项](11-现有前端OpenAPI契约差异与冻结项.md)。 |

场次归属大会届次，场次与嘉宾可多对多关联。前台和运营后台都是业务入口，按所属领域读写。已存在的 Maven 模块仅反映骨架结构。未来领域随实际业务落地，独立部署与否取决于业务需要。

## 依赖与运行边界

- 客户端经 Gateway 进入业务服务。Identity 提供身份和会话能力，业务服务按 [安全与授权规范](03-权限数据范围组织租户审批.md) 保护用例。
- 业务域独占其主数据的写入责任。服务之间通过内部契约、事件或读模型交换数据。同库部署也禁止跨服务直读直写表、依赖对方的 Mapper 或导入对方内部实现。
- 外部服务及框架适配留在本领域基础设施边界，依赖方向见 [工程与编码规范](02-工程与编码规范.md)。确有跨服务调用或可靠交付需求时，再选择通信方式和设施。
- 下载受保护文件时，所属业务域先确认访问权限，File 再提供受控的临时访问。对象键本身不构成授权。

## 事务与一致性

- 本地用例由所属服务管理事务。普通报名的名额占用、记录创建和凭证发放在 Activity 的本地事务内保持一致。有容量上限时，名额检查与扣减须原子完成，数据库唯一约束防止同一账号重复报名。
- 核验须检查凭证有效性与业务状态，数据库并发控制和唯一约束保证一份凭证最多成功核验一次。条件更新可用于原子扣减和核验状态转换。
- 跨服务禁止以共享数据库事务更新多个领域。跨域流程须明确事实来源、失败恢复与重试边界，接收方对重复交付幂等。需要可靠事件交付时可评估 Outbox、Inbox 及事件版本管理。
- 基础报名和到场统计由 Activity 提供。跨域分析以各域确认的事实为来源，复杂分析可按需建设可重算读模型。
